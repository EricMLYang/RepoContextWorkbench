## 一、初始目的與目標

> ⚠️ 這一節是**我從素材回推出來的版本**，不是你親口說的。如果跟你心裡想的不一樣，這節是最該被改掉的一節。

### 1.1 一句話問題

> **我的工作已經有兩套跑得不錯的 agent 產線（寫作、PM），但它們的互動形態全部停在「我打開終端機、打字、等回應」。當工作本身是跨五條產品線的訊號收斂與判斷時，這個形態是不是本來就搭不上？**

### 1.2 觸發這個問題的三個具體體感

1. **看到 Orca 的操作單位轉移**——傳統 IDE 的操作單位是「檔案 + 一個開發者」，Orca 換成「Agent session + worktree + 任務 + 修改結果」。你自己在 8/26 那篇寫下的判斷是：**操作單位變了，工具形態才會跟著變**。那如果我的工作的操作單位不是檔案、也不是程式碼，是什麼？
2. **看到 Tony 為自己造 BAT**——他不是為了做產品，是為了消除自己「iTerm + 幾個終端 + IDE 切來切去」的疲勞。而 ToanyQ 那句「我怎麼這麼忙著下最簡單的指令」，你自己讀出來的結論是：**他不是不研究工具了，是研究完了**。你還沒研究完，所以還在研究。
3. **兩套 harness 的維運都在同一個地方斷掉**——`card_notes` 的 weekly-sync / review-publishing 六週沒跑（缺觸發器）；`PM_Head_work` 的 `0_portfolio/` 五個檔停在 5/22（缺自動化）。**技能都在，就是沒有東西讓它們自己動起來。**

### 1.3 目標的三個層次（由具體到抽象）

| 層 | 目標 | 判準（怎麼知道做到了） |
|---|---|---|
| **L1 消除疲勞** | 把「我記得要做」的心智負擔轉成系統的事 | 週回顧、季檢討、成效抓取這類週期動作，不靠我記得也會發生 |
| **L2 換互動形態** | 找到適合我這種工作（訊號收斂 + 判斷）的互動介面，而不是繼續用 chat 硬扛 | 我不必開一個新視窗，事情也會找上我；且找上來時我只需要做**判斷**，不需要重新拼湊脈絡 |
| **L3 放大判斷力** | 讓我的判斷產能上升，而不只是產出速度上升 | 每個決定留下痕跡（誰決定的、依據什麼），三個月後能回頭檢驗對不對 |

### 1.4 明確的邊界（現在就該講清楚）

- **不是要做產品**。這是 home-cooked 性質，只服務我一個人。若有東西值得分享，走部門 repo 或 AgentHub，不從這裡外溢。
- **不侷限軟體開發**。事實上我最成熟的那套 harness（寫作）本來就不是軟體開發。
- **不預設要寫程式**。外部案例裡最強的幾個（稅理士、律師、幕僚長）都是純 markdown + 排程 + MCP，沒有自建應用。
- **不是要取代判斷**。判斷是我唯一不外包的東西——這條在你的 `00_context/01-定位與判斷權.md` 和價值觀檔裡都已經寫死了。

## 二、兩個參考專案的思維

### 2.1 Orca（stablyai/orca，MIT，2026-08-27 clone）

**它自稱是什麼**：ADE（Agent Development Environment），不是 IDE，也不是模型——是架在所有 CLI Agent 上面的一層統一工作介面。README 的定位句：*The AI Orchestrator for 100x builders.*

**它實際提供的能力（挑跟互動形態有關的）**：

| 能力 | 解決什麼互動問題 |
|---|---|
| **Parallel Worktrees** | 同一個 prompt 扇出給五個 agent，各自隔離工作區，比較結果、合併贏家 |
| **Mobile Companion**（iOS/Android） | 離開電腦後仍能監看與追加指令；agent 跑完會推播 |
| **Annotate AI Diffs** | 在 diff 的任一行留評論再丟回 agent——**審查介面本身變成互動介面** |
| **Design Mode** | 在真的瀏覽器裡點任一 UI 元素，把 HTML/CSS/截圖直接塞進 prompt |
| **Orca CLI** | agent 也能驅動 Orca 自己（`orca worktree create` / `snapshot` / `click` / `fill`）——**介面可被程式化** |
| **SSH Worktrees** | agent 跑在遠端大機器上，本機只是介面 |
| **Notifications / unread state** | 完成或需要注意時通知，可標未讀稍後處理——**收件匣語意** |
| **Account switcher + usage tracking** | 看得到用量與 rate limit reset，可熱切換帳號 |

**它的 `AGENTS.md` 透露的工程紀律**（值得單獨看，因為那是「怎麼讓 agent 安全改自己」的實例）：Design System 單一來源、Reuse Before Reimplementing、註解只寫非顯而易見的、禁止關掉 max-lines lint、禁止 `helpers`/`utils` 這類命名、跨平台一律走 runtime check、SSH 場景的判定詞彙鎖死為 `live`/`unverifiable`/`exited`（**「失聯不等於死亡」被寫成規則**）、遠端 wire 相容性、Git 版本相容性下限 2.25。

**可遷移的思維**：
1. **操作單位轉移**（你自己的原話）：從「檔案 + 程式碼 + 一個開發者」變成「Agent session + 任務 + 修改結果」。
2. **協調層是新的產品層**：模型和 CLI Agent 都是別人做的，Orca 只做隔離、監看、比較、合併——這四件事就是統包商在工地做的事。
3. **介面必須可被 agent 自己操作**（Orca CLI）——**人的介面和 agent 的介面是同一個**。

### 2.2 Better Agent Terminal（tony1223/better-agent-terminal，MIT，v3 Tauri）

**它是什麼**：一個人（Tony Q）為了消除自己的多視窗疲勞而做的終端聚合器，後來變成有 iOS/Android app、有 Homebrew tap、有 pre/正式版發版流程的完整產品。

**它的細節密度說明了什麼**（這才是重點）：

- **Statusline 15 個項目**，含 5h/7d rate limit 用量與 reset 倒數、context %、cache 讀取效率、每輪 cache 成本拆解。
- **Cache TTL 倒數浮動徽章**，只在閒置一分鐘後才出現。
- **Cache 過期警告**：超過 150k cached tokens 已過期（>1 小時）時，送出前跳確認框，避免整包全價重跑。
- **四段權限模式**（Default / Accept Edits / Plan / Bypass）＋ worktree 隔離 preset。
- **Session fork**：從對話任一點分岔並自動送出待發 prompt。
- **Rest/Wake sessions**：暫停與喚醒 session 省資源。
- **Subagent 追蹤**：顯示進度、耗時、卡住偵測。
- 它的 `CLAUDE.md` 裡有一段很有意思的自我宣告：「**Our status line implementation is superior to external alternatives. Do not replace it.**」

**可遷移的思維**：
1. **痛點的顆粒度決定工具的價值**。這些功能沒有一個是「AI 應用」，全部是「我每天被這件事煩到」——cache 過期重跑很貴、不知道還剩多少額度、長任務卡住看不出來。
2. **儀表板不是裝飾，是驗收介面**。他把「我怎麼知道現在狀況如何」做成 15 個可拖拉排序的欄位——這是**把監看這件事產品化**。
3. **反璞歸真是果實不是起點**（你自己 8/26 的結論）。他能只下最簡單的指令，是因為工具磨到跨平台都穩了。

### 2.3 兩者的共同結構（三條）

1. **都不是為了做產品才做的，是為了自己的工作方式才做的**——然後才變成產品。
2. **都選擇做「協調層 / 環境層」，不做模型也不做 agent**——押的是「模型會一直換，但我對工作環境的控制權不該跟著換」。這正是你 `00_context/08` 裡抄下來的那句 harness 信念：「畫面上每一塊都是自己掌控的工具，AI 大廠怎麼改版都能順著吃到，不被單一 IDE/CLI 綁住。」
3. **都把「監看」與「審查」當成一等公民**——worktree 比較、diff 標註、statusline、subagent 進度、通知與未讀。**它們花在「讓我看得見」的力氣，不亞於花在「讓 agent 做事」的力氣。**

### 2.4 我對它們已經下過的判斷（來自 8/26 兩篇草稿，直接引用）

> 「傳統 IDE 的核心操作單位是檔案、程式碼、還有那個唯一的開發者。Orca 的核心操作單位是 Agent session、worktree、任務、修改結果。」

> 「統包商同時管好幾個工班，靠的是三件事——工班之間不打架（隔離）、監工盯得到進度（監看）、驗收標準先講清楚（審查）。Orca 想當的就是那個工務所。」

> 「先想清楚自己的工作裡，哪些任務切得出乾淨的邊界和驗收標準，比先裝哪套工具重要。切不出來的話，再漂亮的工務所，管的也只是一群在同一面牆上施工的工班。」

> 「反璞歸真不是省掉基礎工程，是基礎工程做完之後，你終於可以只講重點。」

**這四句合起來已經構成一個半成品的立場**：工具形態要跟著操作單位走；協調層的三件事是隔離/監看/審查；前提是任務切得出邊界與驗收標準；而基礎工程做完之前不要假裝可以跳過。

## 三、外部案例（不侷限軟體開發）

### 3.1 理論骨架：為什麼「自己做給自己用」是一件正經事

| 論述 | 作者／出處 | 核心主張 | 對我的意義 |
|---|---|---|---|
| **An app can be a home-cooked meal** ✅ | Robin Sloan（小說家，非工程師）| 做 app 可以像做菜——不必成為主廚才下廚。他為四口之家做了 BoopSnoop，無登入、無聯絡人管理 | 「自己做」的正當性跟效率無關 |
| **Five years of home-cooked apps** ✅ | Robin Sloan（2025 續篇）| LLM 是 home-cook 的「超級食物調理機」，但重點不是速度是**主權**：「home-cooked apps 除非我們想要，否則不會改變」——個人軟體**被允許「就這樣完成了」** | 對照商業工具永遠在改版，這是我最該想的一條 |
| **Home-Cooked Software and Barefoot Developers** ✅ | Maggie Appleton | 提出 **barefoot developer**（借自赤腳醫生）：技術上夠聰明但非專業、嵌在社群裡的人。他們卡住的不是寫程式，是「**語言模型的樂高缺少膠水**」（部署、資料庫、權限）。另主張**資料必須留在本機** | 我就是 barefoot developer 的典型畫像 |
| **Malleable Software**（2025 論文）✅ | Ink & Switch（Geoffrey Litt 等）| 四原則：**gentle slope**（使用者到創作者不該有懸崖）／**tools over applications**（做刀不做切酪梨器，前提是共享資料 + UI 可組合）／**scrappy aesthetic**（粗糙的工具才有人敢改）／**communal creation** | 「粗糙美學」對我的 skill 庫是直接的設計建議 |
| **Software for One** ✅ | Adam Waxman | 為家人做睡眠追蹤、果昔份量、馬拉松訓練計畫；一週的晚上做一個，月成本約 160 美元。結論：「**想像力現在才是限制因素**」 | 成本結構已經不是障礙 |
| **Tools for Conviviality**（1973）🔗 | Ivan Illich | convivial tool ＝讓使用者行使自主與創造力的工具，對照侵蝕自主性的工業工具。近期延伸主張很尖銳：**AI 當「工具」時是 convivial，當它變成替你做決定的 agent 形態時就不是** | 這句話是對「全自動化」最有力的反方 |

> Ink & Switch 的一句警語值得單獨標出：**「把 AI coding 工具帶進今天的軟體生態，就像帶一位優秀的副主廚進美食廣場。」**——沒有可組合、可本地修改的底層，AI 也放大不了什麼。

### 3.2 非軟體專業者自建 AI 工作流（挑最硬的十個）

| 人 | 領域 | 做了什麼 | 最值得偷的設計 |
|---|---|---|---|
| **畠山謙人** 🔗 | 京都稅理士（自述不會寫程式） | 0 員工帶 60 家顧問客戶、17 點下班。Claude Code + freee API 每晚 21:00 自動記帳，5 小時 → 50 分鐘 | **二段判斷**：先用「14 分類 × 100+ 詞關鍵字字典」硬規則判，**匹配不到的才丟給模型**。另有送出前去識別化、CLAUDE.md 當「事務所憲法」（角色／可執行業務／禁止事項／工具連接圖四區塊） |
| **Paula Rojas** ✅ | 智利訴訟律師（零技術背景） | 三個工具：起訴狀進案（1 小時→5 分鐘）／書狀起草 agent（用她自己的聲腔）／**每週開庭表監控**（Playwright MCP 跑 100+ 案號，40-60 分鐘→自動，至今零錯誤還抓到一次人工漏掉的開庭） | **「沒有人單獨做任何不可逆的事」**——所有產出離開事務所前都要她核可。書狀先要**策略計畫**才要草稿 |
| **Ahmed Elsonbaty** ✅ | 開羅心臟麻醉醫師 | 床邊臨床決策支援工具，現 150 國逾 1 萬名醫師在用，論文被期刊接受 | **刻意不用生成式 AI 產最終答案**——「同一個問題問 100 次要出現同一個答案」。AI 只用來畫骨架，知識庫手工從文獻建。**R3 風險的解法不是加審查，是換架構讓輸出變確定性** |
| **Maak.sh** 🔗 | 日本司法書士 | 「法務 OS」三層：Master Instruction（**禁止 AI 客套與同情，強制邏輯輸出**）／RAG（法令與登記先例）／Output（**用 Python 驗算稅額**並附條文依據） | **一人事務所沒有覆核者，就用系統當覆核者** |
| **Jaemark Tordecilla** ✅ | 菲律賓調查記者 | 專讀審計署冗長報告的 custom GPT，只摘「重大審計發現」一節、上傳後**不自動摘要而是先問你要什麼**、再用提問引導記者往下挖。約省 80% 讀報告時間 | **16 小時全花在「限制」上，不是功能上** |

### 3.6 五篇重要論述（「介面即槓桿」這條線的骨幹）

**① LangChain — Introducing Ambient Agents（Harrison Chase）** ✅
最直接針對這題的一篇。原話：chat 造成 *unnecessary interaction overhead, limit the ability of us humans to scale ourselves, and fail to use the full potential of LLMs*。Ambient agent 改為「監聽事件流並據以行動，可同時處理多個事件」。**但他明確強調 ambient ≠ 全自動**，因此提出三種人在迴路型態：**notify（只告知不行動）／question（卡住時問你）／review（高風險動作先送審）**，另加 edit 與 **time-travel**（回到早先某個決策點給回饋）。UX 上他**反對用 Slack 承載**，主張另建仿 email／ticketing 的 **Agent Inbox**——好處是待處理事項集中、可排優先序、可追蹤未結案。
→ https://www.langchain.com/blog/introducing-ambient-agents

**② SWE-agent — Agent-Computer Interfaces（arXiv 2405.15793）** ✅
「介面即槓桿」最硬的學術背書。核心概念：**把語言模型 agent 當成一種全新的終端使用者**，它有自己的需求與能力，值得為它專門設計介面（ACI）。實證：同一個模型，把 Linux shell 換成簡化、對 LM 友善、有立即回饋與護欄的命令集，效能大幅改變。**可遷移的判斷：你給 agent 的介面設計，比你給它多少工具更決定成敗——而這句反過來也成立。**

**③ Karpathy — Software 3.0 與「自主度滑桿」** 🔗
反對一步到位做全自動 agent，主張做**部分自主的產品配上自主度滑桿**（autonomy slider）——自主不是 0/1 開關，是可轉的旋鈕。第二個論點：**生成—驗證迴路必須夠快**。AI 生成速度已超過人驗證速度，新瓶頸是「審查輸出並判斷對不對」。因此好 GUI 的價值在於**讓人類的驗證迴路快到爆**，而不是讓 AI 看起來更聰明。

**④ Levels of Autonomy for AI Agents（Knight Institute / arXiv 2506.12469）** ✅
目前最清楚的人機分工分級，用**「人扮演什麼角色」**定義，不是用「AI 多強」：

| 級 | 人的角色 | 內容 |
|---|---|---|
| L1 | **Operator** | 人掌握所有規劃，agent 提建議、須明示核准才執行 |
| L2 | **Collaborator** | 雙方都能規劃與執行，頻繁往返，人可**直接編輯** agent 的產出 |
| L3 | **Consultant** | agent 長時間主導，人**不能直接編輯**，只能透過訊息給方向；agent 在關鍵時刻主動諮詢 |
| L4 | **Approver** | agent 自主執行既定計畫，只有卡住／失敗／需憑證或重大動作核准時才找人 |
| L5 | **Observer** | 完全自主，人只能看 log 和按緊急停止 |

**最重要的設計洞見：自主度可以獨立於能力來設計**——很強的 agent 仍然可以被設計成每步都問你。它另外區分 autonomy（多不需要你）與 agency（工具多不多）。

**⑤ Amelia Wattenberger — Why Chatbots Are Not the Future of Interfaces**（2023）🔗
「chat 是局部最佳解」論證的原點。核心：**好工具會用外形告訴你怎麼用它、以及不該怎麼用它**（affordance）；chat 只給你一個輸入框，長得跟 Google 搜尋框、登入表單一模一樣，因此**把「學會怎麼用」的成本丟給每個使用者各自摸索，而這本來可以烘焙進介面裡**。這篇是後續 generative UI、agent inbox、agentic grid 一整條路線的思想來源。

> **補充框架**：MIT CISR 的 **AI Decision Matrix**（ambiguity × risk 兩軸決定 decision rights，並分別調整 AI 在**框定決策／執行決策／從結果學習**三件事上的參與度）；Mollick 的 **Centaur vs Cyborg × Jagged Frontier**（顧問用 GPT-4 在能力邊界內任務多完成 12.2%、快 25.1%、品質高 40%；但在**刻意選在邊界外的任務上，用 AI 的人答對率反而低 19 個百分點**）。

### 3.7 跨案例共通模式（九條）

> 把 50 個案例攤開比對後重複出現的結構。前五條是「怎麼開始」，後四條是「怎麼不死掉」。

**A. 起點永遠是「煩」，不是「機會」**
沒有一個案例是先看到 AI 能力再去找應用場景。最精準的表述：**「改進的信號不是『我應該優化』，而是『我覺得這很煩』。」** Alex Craig 把這件事制度化成每週五的 **Desire Paths 掃描**——回顧「我這週在哪裡繞了路」，然後只自動化一個。

**B. 第一個工具幾乎都落在同一個位置：「每天早上重建脈絡」**
跨產業、跨語系，**morning brief 是命中率最高的第一個 skill**（Brillhart、Obie、Craig、Rodríguez、Murchison、高野秀敏、横峯樹、Esor 全部都有）。第二名是 **1:1 / 會議準備**（拉該人近期活動＋上次筆記＋未結話題）。
💭 推論：這不是巧合。管理者最大的隱性成本是「每次切換脈絡都要重新拼湊」，而這正是 agent 唯一能無損接手的事——**它不需要判斷，只需要記得**。

**C. 資料層是純文字資料夾 + git，不是應用程式**
凡是撐過三個月的，真相層幾乎都是 markdown + 檔案系統。資料庫只出現在**遙測與狀態層**，從來不是起點。最好的措辭：**「Own your context layer. All memory lives in plain text files, not vendor systems.」**

**D. 主戰場是 context，不是 prompt**
Wix 的 Altarescu 講得最省：**「投資 context，不要投資 prompt。」** 同一件事的不同說法：畠山的「事務所憲法」、高野的「寫給新人的業務手冊」、Karpathy 的 schema 層、reona777 的 CONTEXT.md + SPEC.md + ADR。
**反面教材同樣清楚**：水口貴史把所有需求都塞進 CLAUDE.md，需求定義與指令混在一起燒掉大量 token——修正方式是把「應用設計」與「給 AI 的指令」**分離**。

**E. 領域知識是護城河，非工程背景是優勢而非缺陷**
Grant Blashki：不會寫程式反而是優勢，因為外包會流失細微的臨床脈絡。Jake Northrup：**「事務所的 IP 才是地基，技術是大宗商品。」** 藤井：**「AI は言語化できる人のツール」**（AI 是給能把事情講清楚的人用的工具）。

**F. 硬規則優先，LLM 只吃殘差** ←（研究員認為最被低估、最可移植的一條）
畠山用關鍵字字典先判、匹配不到才給模型；De Jesus 讓確定性規則吃掉 80%；Elsonbaty 直接不用生成式產最終答案；Maak.sh 用 Python 驗算稅額。
效果是三重的：**省錢、可稽核、失敗可預期**。而且它自動解決了「高風險任務怎麼辦」——**不是加審查，是換架構。**

**G. 驗收機制必須是非工程師自己能執行的**
あろか讓 AI **演「兩位資深工程師的對話」**做結構化 review；reona777 把判斷邏輯抽成純函數 + 308 個測試（把「我不會讀 code」轉換成「測試過就是對的」）；Maak.sh「一人事務所沒有覆核者，就讓系統當覆核者」；Paula Rojas「沒有人單獨做任何不可逆的事」。

**H. 不可逆動作設閘門，信任漸進升等**
Feld：不可逆動作須人核可，**且任何編輯都重置關卡**。De Jesus：三個信任層級（需核准→監督→自主）靠績效指標升等，**VIP／家人聯絡人有寫死的安全閘**。mboverell：**Read-first, write-cautious**。
💭 這一組直接對應你的 R0–R3 × Gate A–E，而且比多數理論框架更具體——特別是「**任何編輯都重置關卡**」，是實際被燙到過的人才寫得出來的。

**I. 架構往簡單收斂；skill 是「升格」出來的，不是設計出來的**
PostHog 三 agent 拆回單 agent，少 300 行、更可靠；Feld 不建 orchestration layer；Obie 讓 Claude 自己長結構、**重複出現的 workflow 才升格成 skill**；Craig「系統是靠累積的修正長出來的」；横峯樹「**完璧を目指さない**」（各任務獨立執行、一個掛掉不影響其他，寧可每天穩定 80 分）。
唯一的反向意見是 Barbara Bermes——她保留通用 orchestration 骨架，因為那讓她 30 分鐘就能生一個新 agent。💭 折衷讀法：**骨架可以複用，編排邏輯不要複用。**

### 3.8 業界的空白區（研究員標為推論，但值得特別注意）

**1. 審批疲勞（approval fatigue）沒有解，而且正在變成資安破口** ✅
有具體數據：即使自動核准率高達 95%，一個 300 次工具呼叫的 session 仍會彈出 15 次人工審查——15 次上下文切換，而人被打斷後平均需 10-15 分鐘才回到有產出的狀態。行為模式描述得很準：「第一次請求，人會仔細讀；第十次，開始略讀；再往後，句子還沒讀完就按核准了。」2026-03 已出現對應攻擊手法分類 **"Human Approval Fatigue Exploitation"**。目前唯一像樣的設計原則是**「打斷必須自己掙得」——只有三種情況值得中斷你：動作不可逆、爆炸半徑碰到你賠不起的東西、或 agent 自評信心低。**

**2. 非開發領域沒有 verification harness，這是最大的一塊空白** 💭
Coding agent 能高度自主，是因為有 test / CI / diff / lint 這套**便宜且客觀的驗證基礎建設**。但「一份彙整報告」「一個資源配置決策」「一份會議紀要」沒有等價物——你可以叫 agent 寫週報，但**沒有 CI 告訴你它寫錯了**。Anthropic 的 **outcomes**（用 rubric 讓另一個 grader 評分）是目前唯一在產品層級處理這件事的嘗試，還在 research preview。
→ **推論：對非開發工作，自主度天花板是被驗證能力鎖死的，不是被模型能力鎖死的。**

**3. Fan-out 成熟，fan-in 完全空白** 💭 ←（**對我最直接的一條**）
「一題丟給 N 個 agent」已經有成熟介面（worktree、best-of-N、agentic grid）。但**反方向沒有人做**：把 6 個子 repo 的近況 + ClickUp 看板 + 幾場會議記錄 + inbox 零散訊號，收斂成一份「所以我現在該怎麼判斷」。這是扇入工作，需要的介面是「多來源 → 一個判斷」，而現有工具全部是「一個 prompt → 多個結果」。Hebbia Matrix 的格子最接近，但它處理同構文件，不是異構訊號源。

**4. Agent Inbox 沒有標準，正在製造新的收件匣碎片化** 💭
Zed 的 ACP 標準化了「編輯器 ↔ agent」、MCP 標準化了「agent ↔ 工具」，但**「agent ↔ 人的審核收件匣」沒有協定**。同時用三種 agent 就有三個待辦收件匣——恰恰複製了 agent inbox 原本要解決的問題。

**5. 記憶的治理層缺席** 💭
Dreaming 已經有「審核後才生效」和「來源引用」，但沒有工具回答：**這條記憶是誰核准進來的？它影響過哪些後續決策？當它被證明是錯的，受它影響的產出要不要重審？** 對要為決策負責的管理者這是硬需求，對工程 agent 只是 nice-to-have，所以沒人做。

**6. 手機端仍然只能「監看與批准」，不能「完成」** ✅
Every 的實測結論：「你在手機上永遠沒辦法把事情做完，因為你沒辦法載入 app 驗證它能跑。」💭 對非程式工作這個限制可能較輕（審一份報告的結論比驗一個 UI 容易），但目前沒有產品把「手機上可完成的審核」當成設計目標。

**7. Proactive 的「該不該打斷你」靠規則，不是對你注意力的模型** 💭
所有 proactive agent 的觸發都是 if-this-then-that。**沒有一個系統知道你現在在做什麼、被打斷的代價多少、這件事能不能等到你下一個空檔。**

**8. 沒有「決策留痕」介面** 💭
那些人機分工框架（5 級自主度、MIT 矩陣、centaur/cyborg）**全部是規範性的——告訴你「應該」怎麼分工，但沒有任何一個附帶量測回饋**。沒有工具在記錄「這個決定是我做的還是 agent 做的、根據什麼、三個月後證明對不對」。而 trust calibration 的本質需要回饋閉環：**你無法校準一個你從不量測的東西。**
→ 這剛好對應本 repo 「案例回訪／建議採納率仍待補追蹤」的缺口——**不是我獨有的問題，是整個產業都還沒解。**

## 五、我自己已經想過的（卡片立場盤點）

> 298 張卡裡有 47 張直接談 agent 工作流。以下是已經成形的立場，以及自己標記過但還沒解的對賭。

### 5.1 五個已經成熟的立場

**① 控制介面已經從 Prompt 換成 Evaluation。**
生成邊際成本趨零後，人對系統的控制點是「我怎麼知道它做得對不對」。三個尺度的同一表述：軟體是 TDD / Interface+Test、資料是 Data Contract、Agent 是 Evals。具體做法已經寫死：**用 code 定規格、用 code 定驗收，這兩層親自逐行 review 並保護起來不讓 AI 改，中間全交給 Agent 跑到通過。**
> 「沒有評估，就沒有控制；沒有控制，就無法落地。」
> 「上不去的是責任——出事時『沒有人讀過那段 code』不是能站上檢討會議的答案。」

**② Harness 是品味的具體實現，而且它的改進來自軟體工程而非模型升級。**
> 「你的 Harness 就是一面鏡子，映照出你的價值觀。在複製貼上 Agent 的世界裡，價值觀就是差異化。」

**③ 信任是配置題不是判斷題。**（我認為這是全庫最有原創性的一條）
> 「它問的是『在哪一塊、可以信到什麼程度、可以押多少資源』。……多數不是完全看錯一個人，是把對方擺錯位置。」
建倉四動作可直接平移到 Agent：**用樣本不用承諾／從小部位開始／主動還權／做久一點。**
第二次重框更關鍵：把主控變數從「單筆信賴度」換成 **artifact 的生命週期階段**（Draft → Promotion Gate → Published），讓模糊的權限討論變成「狀態轉移由誰觸發」的明確規則。

**④ Loop 化有三條硬條件，不是想 loop 就 loop。**
可量測 metric ＋ 失敗代價可控 ＋ harness 夠硬，三條同時成立才行。而 Loop 相對 harness 真正新增的只有兩個元件：**Automations（去人化觸發）與 Memory（跨次持久狀態）**。
配套的警告：**Stop Condition 的真風險是被控的 Agent 主動繞過**——「停止條件由 Agent 自己在迴圈中執行，等於把控制權交給被控對象」，必須設在 Agent 不能自我修改的層級。

**⑤ 記憶設計的核心是壓縮與過濾，不是儲存與檢索。**
四層（工作記憶／對話摘要／任務製品／長期偏好），**不要預設用 Vector DB**。前提數據：agent 運行時 84% 的 context 被工具觀察結果佔據。
配套的組織觀：**傳統組織設計本質是 context 成本最佳化的產物，而 Agent 的 context 成本結構跟人類相反**——人的 context 集中、昂貴、不可分切，所以「一人多工」；Agent 的 context 輕量、可分切、便宜，所以最佳解是「一事一 agent」。**照搬人類組織圖是浪費 Agent 的結構性優勢。**

## 六、素材交叉後浮現的張力

> 這一節只列張力，**不給答案**。它們是下一輪思考的入口。

**1. 我的兩套 harness 都很成熟，但都是「同步、我開場、我在場」的形態。**
外部研究列出的 19 種形態裡，我實際在用的只有 #1（chat）和一點點 #10（subagent 扇出）。形態 4（ambient）、5（排程）、6（事件）、7（agent inbox）、18（dreaming）**我一個都沒有**——而我所有的維運債務（4.4 的第①類）恰好全部落在這幾個形態該解決的位置。

**2. 「造工具的力氣遠大於用工具」這件事，可能不是病，也可能是病。**
`.github/skills/` 異動 217 次 vs digest 產出 23 次；`create-work-ppt` 有 3 個 commit 在調 logo 大小。ToanyQ 會說這是「鬼東西」，而我自己的反駁是「他是研究完了，我還沒」。但 Alex Craig 的原則是「**系統是靠累積的修正長出來的，不是預先設計出來的**」，Obie 的原則是「**重複出現的 workflow 才升格成 skill**」——**這兩條都在說：先用、後造。而我 8/21 的自我診斷正好是「重組本身變成一種循環，吃掉維運精力」。**

**3. 我的工作主體是 fan-in，但市場上只有 fan-out 的工具。**
把 16 個 repo 的近況 + ClickUp 三個 Project + 週會續辦 + inbox 零散訊號 + 幾場會議，收斂成一份「所以我現在該怎麼判斷」——這是異構訊號扇入。研究員的結論是這一塊**市場空白**（3.8 第 3 點）。而 Orca / BAT 兩個參考專案，做的都是扇出。**它們的思維可以借，形態不能直接搬。**

**4. 非開發工作沒有 CI，所以自主度天花板不是模型鎖的，是驗證能力鎖的。**
這跟我自己第 ① 條立場（控制介面已換成 Evaluation）完全一致，但也把問題推回來：**我的「週會報告」「portfolio 狀態」「決策記錄」的 evaluation 長什麼樣子？** 外部案例給的三個候選答案是：硬規則先吃 80%（畠山、De Jesus）、系統當覆核者（Maak.sh 用 Python 驗算）、rubric grader（Anthropic outcomes）。

**5. 「主軸」是 agent 產不出來的那一塊——這剛好是我的判斷權所在。**
`weekly-meeting-prep` 已經有很嚴的寫作規範（禁 repo 名／禁內部代號／禁「待補」／每條過 So what），但 git log 顯示 0728 那版仍是「初稿（含使用者手改主軸）→ 全文重寫 → 主軸再改寫」。**Agent 產得出結構，產不出主軸。** 這既是好消息（我的判斷權還在）也是壞消息（週會報告的 3-4 輪返工不會因為 skill 變好而消失）。

**6. 深夜／週末的我和白天的我，需要的互動形態可能相反。**
`card_notes` 尖峰 23:00 且週末活躍——那是**不希望被打斷**的深度工作。`PM_Head_work` 尖峰 16:00 且週六幾乎不動——那是**必須被打斷得起**的協作工作。而所有 proactive agent 的觸發都是 if-this-then-that，**沒有一個系統知道我現在在哪個模式**（3.8 第 7 點）。

**7. 我已經有「決策記錄」的規範，但它是全 repo 執行最差的一條。**
16 條決策只有 1 條有完整記錄檔。而外部案例裡 Obie 的 `/decide`（**連同「當時考慮過的替代方案」一起寫**）和 Pooja Mathur 的 append-only decision log（`[date] DECISION: | REASONING: | CONTEXT:`）都證明這件事做得起來。同時 3.8 第 8 點指出**整個產業都沒有「決策留痕」介面**——這既是我的缺口，也可能是我最有條件做的東西（因為我本來就是靠判斷吃飯的）。

**8. 兩個參考專案都花了大量力氣在「讓我看得見」，而我兩套 harness 的儀表板都是空的。**
BAT 的 15 項 statusline、cache 過期警告、subagent 卡住偵測；Orca 的通知與未讀、用量追蹤、diff 標註。而我這邊：`workspace-stats` 存在但沒在跑、`repo-healthcheck` 存在但沒在跑、LinkedIn 成效停在 7/05、skill 使用率完全沒量。**Feld 的「靜默遙測 hook，且永遠 exit 0」是唯一在 50 個案例裡真的量了「有沒有人在用」的做法。**
