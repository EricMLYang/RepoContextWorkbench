## 0. 先講結論

**一句話**：11 個工具查完，**沒有一個是我要建的東西的競品**——「把 N 個 repo 的異構訊號收斂給一個人下判斷、懂我的四個場合、通知自帶行動出口」這個形狀市面上是空的。它們對我的自建的價值分三種角色：

- **零件**：我的工具直接呼叫、不重造的底層管線
- **設計課**：值得抄進我的規格的設計決策（省掉自己試錯）
- **反面教材**：已經有人死過一次的死法，我不能重複

## 一、讀法：這是拆機報告，不是選購指南

我要建的工具的形狀（收斂檔 v3 已定）：**常駐環境層監控 ＋ registry ＋ 資料脊椎 ＋ 挑撞落生四動詞 ＋ 四個場合**。這一輪查證確認：市面上沒有這個形狀。所以每個工具先花力氣**看懂它**（它是什麼、為什麼這樣設計、用什麼做的），再問三件事：

1. **它有沒有我可以直接接的零件？**（有 API／MCP／CLI／webhook 可被我的工具呼叫的才算；只有人類介面的不算）
2. **它做了哪些我可以抄的設計決策？**（schema 怎麼切、互動怎麼設計、摩擦怎麼降）
3. **它死在哪裡、或它會害我死在哪裡？**（反面教材）

拆完後的分工圖——**我建的層 vs 接零件的層**：

```
╔═ 我建：體驗層（何時、以何形式、帶什麼行動出口出現）═╗   ← §7：全市場空白
║  四個場合的排程與觸發｜通知形狀｜打斷判準            ║
╚═══════════════════════╦══════════════════════════════╝
                        ↓
╔═ 我建：語意層 ═══════════════════════════════════════╗
║  registry 上半身（血統/tier/關係/語意標籤）           ║   ← 抄 mani 骨架，語意獨門
║  脊椎（append-only 留痕）                             ║   ← 對照 second-brain，補 open loops
║  挑（語意建議）｜撞（已知/衝突/真增量）｜生（出生登記）║   ← 全獨門
╚═══════════════════════╦══════════════════════════════╝
                        ↓ 呼叫
╔═ 接零件：管線層 ═════════════════════════════════════╗
║  release 訊號 ← NewReleases.io（webhook/API）         ║
║  repo 打包   ← Repomix（MCP/CLI）、gitingest（捕捉）  ║
║  git 狀態    ← 自有 repo-git-sync；欄位規格抄 gitpane ║
║  落          ← 沿用 inbox-dispatch 慣例               ║
╚══════════════════════════════════════════════════════╝
```

**一句話讀法**：**管線接現成，判斷自己建。** 凡是「把資料從 A 搬到 B」的，別人做得比我好，接上就是；凡是「決定什麼時候、以什麼形式、帶什麼下一步出現在我眼前」的，沒有一個工具知道我有四個場合——那就是我的工具本體。

## 二、組 A：多 repo 狀態工具 —— registry 與採集層的設計課

這三個都沒有可程式化的介面能讓我直接接（gitpane/GitKraken 是給人看的、mani 是 fan-out 執行器），所以這一組的價值**全部是設計課**：它們各自替我試錯了 registry 和採集層的一部分設計。

### 2.1 gitpane —— 終端裡的多 repo 儀表板

**它是什麼**（標語原文：*Multi repo Git workspace dashboard for the terminal*）✅
一個 TUI（終端全螢幕介面）應用，解決「repo 一多，逐個查狀態查不動」的問題：一個畫面同時盯住幾十個 repo。三欄式版面——左欄 repo 清單（每個 repo 顯示分支、是否 dirty、ahead/behind 幾個 commit、worktree 數量、變更檔案數）、中欄變更檔案、右欄 commit 圖（lane 式渲染，最多 200 個 commit）。可以鑽進單一 repo 看 split diff、直接執行 push／pull／rebase（會自動解析 upstream）；裝了 `gh` CLI 還能看該 repo 的 issue 與 PR。支援滑鼠、可自訂快捷鍵。✅

**設計哲學** 💭
它是為「**多 repo ＋ agent 並行**」這個新工作形態設計的——README 明講適用場景是 microservices、含 submodule 的 monorepo、**以及 agent 並行開發**：它有 worktree 感知，還會**偵測 worktree 上活著的 agent**。三個立場讀得出來：(1) **不離開終端**——監看應該發生在你已經在的環境裡，不是另開一個網頁；(2) **事件驅動而非輪詢**——用檔案系統監看（notify）即時更新，便宜且即時；(3) **看與做在同一個畫面**——看到 dirty 就地 push，不用切去別的工具。

**技術棧與使用方式** ✅
Rust（MSRV 1.88）／TUI 框架 ratatui＋crossterm／git 操作走 git2-rs（libgit2，不是殼層呼叫 git 指令）／非同步 tokio／檔案監看 notify。跨平台（Linux／macOS／**Windows**）。安裝：`cargo install gitpane` 或單行 shell 裝預編譯檔。已知坑：符號連結不跟隨；「`.git` 是檔案」的 worktree／submodule 要手動寫進 `pinned_repos`；GitHub 面板要 `gh` 已登入；Linux 的 worktree 監看預設關（怕 inotify 爆掉）。

**成熟度**：129 stars／4 forks／585 commits，CI 完整、開發活躍。✅ 💭 小專案但不是玩具——585 commits 的密度說明作者自己天天在用。

**對我的自建——可抄的設計決策** 💭
1. **狀態欄位清單就是我採集層的 spec 起點**：分支／dirty／ahead-behind／worktree 數／變更檔案數，這五欄不用自己從零想。
2. **事件驅動監看（notify）而非輪詢**——常駐環境層想要「即時但便宜」，這是驗證過的做法，連「inotify 會被灌爆所以 worktree 監看要 opt-in」這種坑都替我踩了。
3. **agent 偵測**——11 個裡唯一感知「這個 repo 上有 agent 正在跑」的；等我的工具要做這件事（呼應素材檔 §2.1 Orca 的 Parallel Worktrees），這裡有參考實作。

**對我的自建——反面教材與它停在哪裡** 💭
它是一個**你要前往的頁面**：做得再細，只要形態是「開個 TUI 去看」，就踩在我 `repo-healthcheck` 的死因上（§7）。而且它不懂語意——知道 repo 有沒有 dirty，不知道「這三個 repo 跟我現在想的事情有關」，「挑」這個動詞它一個字都碰不到。

連結：<https://github.com/affromero/gitpane>

### 2.2 mani —— 宣告式的多 repo 指令執行器

**它是什麼** ✅
Go 寫的 CLI，解決「同一個指令要對很多 repo 跑」的重複勞動：用一份 `mani.yaml` 描述「我有哪些 repo、各屬哪些 tag」，然後對任意子集執行任意指令。`mani init` 掃描目錄、自動把含 `.git` 的資料夾寫進設定檔；`mani list projects` 看清冊；`mani exec --all --parallel --output table git status` 對全部 repo 平行跑 git status 並輸出成表格。

**設計哲學** 💭
**宣告式＋組合式的 Unix 路線**。它把世界拆成三個正交概念——**projects**（我有哪些 repo）、**tags**（它們怎麼分群）、**tasks**（我常對它們做什麼，本質就是 shell 指令）——然後讓三者自由組合。它不想當平台、不存狀態、不開 daemon，就是一個「文明版的 for-loop」：一份純文字設定檔就是全部的真相，Go 的並行能力負責跑得快。這種「小而正交」的設計是它跟 GitKraken 全家桶路線的根本分歧。

**技術棧與使用方式** ✅
Go（利用其並行處理多 repo）。單一 `mani.yaml` 設定檔。安裝：Homebrew／AUR／Nix／直接下載執行檔。⚠️ **Windows 支援不完整**（官方說主要支援 Linux/macOS）——對我是硬限制，我兩個平台都用。

**成熟度**：756 stars／197 commits。✅ 三個裡社群規模最大。

**對我的自建——可抄的設計決策** 💭
1. **projects／tags／tasks 三分法**——把「清冊」「分群」「動作」拆成三個第一級概念，而不是把 repo 清單寫死在腳本裡。我的 registry 超集（開放問題 #3）第一步就拿這個骨架檢查夠不夠用。
2. **「init 自動掃描 ＋ 手寫補語意」的混合模式**——清冊下半身機器生成、上半身人工維護。我的 registry 該走同一條路：狀態欄位機器填，血統／tier／關係我填。
3. **純文字設定檔＝全部真相**——與我 §9「資產＝純文字資料、程式碼＝耗材」的立場完全同構，這是它比 GUI 工具耐活的原因。
4. tag 機制是「挑（手選模式）」的最原始版本：挑＝按 tag 選子集。動詞鏈第一格可以從這裡起步。

**對我的自建——它停在哪裡** 💭
tag 是靜態的，**不會因為內容變了就變**——所以它到得了「挑（手選）」，到不了「挑（建議）」。它是 **fan-out 的教科書定義**（一個指令 → N 個 repo）；我要的 fan-in（N 個 repo 的異構訊號 → 一個判斷）它完全不碰——素材檔 §3.8-3 那條空白的具體長相就是它。另外我的 `repo-git-sync` 已經是半個 mani，執行層不缺，缺的從來是上面的語意層。

連結：<https://github.com/alajmo/mani>｜作者介紹文在 dev.to/alajmo

### 2.3 GitKraken Workspaces —— 商業全家桶裡的 repo 群組

**它是什麼** ✅
GitKraken（商業 Git 工具，付費訂閱制）的一個功能：把散在 **GitHub／GitLab／Bitbucket／Azure DevOps** 四種代管平台的 repo 收進同一個 dashboard。兩種 workspace——**雲端型**（可分享給團隊、跨裝置同步）與**本機型**。能同時看所有 repo 的分支／變更／警告、一鍵批次 pull/fetch/開啟、新成員一步 clone 整組 repo；**Launchpad** 功能追蹤跨 repo 的 PR／issue／進行中工作。同一份 workspace 定義在 GitKraken Desktop、VS Code 的 GitLens、GitKraken CLI、gitkraken.dev 網頁四處通用。

**設計哲學** 💭
與 mani 完全相反的路線：**整合平台全家桶**。它假設你要的不是零件而是一站式體驗——GUI 優先、雲端同步、跨產品一致、對象是「管理多專案的團隊 lead」。它收斂的對象是**代管平台上的結構化物件**（PR、issue、branch），因為那是商業平台 API 給得出來的東西。這個哲學決定了它的天花板：平台 API 之外的訊號（本地檔案、非 git 的資訊源）進不了它的世界。

**技術棧與使用方式**：商業閉源產品，桌面＋Web＋CLI＋IDE 外掛多形態。付費層需求官網未寫明（雲端 workspace 歷來是付費功能）。💭 未細查——反正不進工具鏈。

**對我的自建——可抄的設計決策** 💭
1. **Launchpad 的概念**：「跨 repo 待辦收成一條流」是三個裡最接近 fan-in 的嘗試。概念可借——但它收結構化物件，我收異構訊號（子 PM 的 `01_inbox/`、card_notes 卡片、tool_experiments 上游版本、ClickUp）；**收異構訊號正是我的工具跟它的分界**。
2. **「同一份設定四處通用」**：desktop／CLI／IDE／web 吃同一個 workspace 定義。呼應素材檔 §2.1 的 Orca 課——**人的介面和 agent 的介面是同一個**。我的 registry 也該這樣：一份定義，儀式讀它、碰撞台讀它、agent 讀它。

**為什麼不進工具鏈** 💭：商業生態綁定，違反素材檔 §2.3「不被單一 IDE/CLI 綁住」；且它服務「團隊 lead 看 portfolio 的 PR 狀態」，不是「一個人決定今天怎麼開場」——場合不對。

連結：<https://www.gitkraken.com/features/workspaces>

### 2.4 組 A 小結：registry 的規格拼圖

| | gitpane | mani | GitKraken WS | → 我的 registry |
|---|---|---|---|---|
| 路線 | 終端儀表板 | 宣告式 for-loop | 商業全家桶 | 純文字資產＋語意層 |
| 清冊怎麼來 | 掃目錄（自動） | yaml（init 自動＋手寫） | 平台 API | **抄 mani：自動下半身＋手寫上半身** |
| 狀態欄位 | 五欄＋agent 偵測 ✅ | 無 | 分支/變更/警告 | **抄 gitpane 的欄位清單** |
| 分群 | 無 | tag | workspace | tag 起步，語意建議是獨門 |
| 語意／血統／tier | ❌ | ❌ | ❌ | **全獨門，沒有對照組** |

💭 **結論**：registry 的規格 ＝ **mani 的骨架 ＋ gitpane 的欄位 ＋ 我的語意上半身**。前兩塊有現成答案抄，第三塊（血統、tier、關係、語意標籤）市面上零對照——這正好回答開放問題 #3 的一半：不必找工具，格式參考已經夠了。

## 三、組 B：release 追蹤 —— 第一個可接的訊號源零件，外加監控層的「形狀課」

### 3.1 NewReleases.io —— 全生態的版本發布通知系統 ⭐

**它是什麼** ✅
SaaS，自稱「軟體版本發布通知系統」：你訂閱在乎的專案，它出新版就通知你，讓工程師不用手動巡邏上游。三類來源幾乎全覆蓋——
- **程式碼代管**：GitHub／GitLab／Codeberg／Gitea／Bitbucket／GNU Savannah
- **套件管理**：PyPI／NPM／Yarn／Maven／RubyGems／Packagist／NuGet／Cargo／Hex／CPAN
- **容器登錄**：Docker Hub／AWS ECR Public／Quay／Artifact Hub

通知管道同樣廣：Email（可設每小時／每日／每週彙整或即時）、Slack／Telegram／Discord／Google Chat／Teams／Mattermost／Rocket.Chat／Matrix、**Webhook**。中間夾一層過濾：regex 版本過濾、pre-release 開關（只收正式版）。還能**批次匯入**——直接餵 `requirements.txt`／`pom.xml`／`go.mod`／`package.json` 就把相依全訂閱。**有公開 API 和官方 CLI**，通知內含 release notes。

**設計哲學** 💭
**通知系統的正統三段式：廣收 → 過濾 → 廣推**。來源與管道兩端都做到極廣（這是 SaaS 的規模優勢，自架者做不到這個覆蓋），中間用 regex 和頻率設定讓使用者自己收斂。最關鍵的一點是它**天生事件驅動**：沒新版＝完全沉默，永遠不會出現「打開看一眼、全部正常」的空巡邏。這不是它設計得特別好，是 release 追蹤這個問題形狀天生如此——而這正是它給我的最大一課。

**使用方式**：註冊訂閱制；免費／付費界線官網首頁沒寫（要看 /pricing，未查）。💭

**對我的自建——怎麼接** 💭
1. **Webhook → 我的收斂層**。release 偵測我一行都不寫；它的通知先進我的系統，**由我的體驗層決定什麼時候、以什麼形式浮出來**——§8「資料採集用現成、體驗層自建」的第一個實例。
2. 短期（工具還沒建時）：直接設**每日彙整**推到我已經在的地方，`tool_experiments` 的更新追蹤就地解決，不用等工具。

**它給的形狀課（比零件本身更重要）** 💭
它天生通過我第八節的「餘光可見」與「無事不報」兩條。反過來告訴我：**我的監控層要長得像 release 通知，不像儀表板**——任何「把當前狀態全部攤開」的設計都是 healthcheck 復發。

**它停在哪裡** 💭：它只會說 hermes-agent 出了 v0.9，不會說「你 README 記的那個 retry loop 痛點，這版修了」——**「這個新版對我哪個 repo 有意義」是撞，是我的層**。

### 3.2 github-release-monitor（iamspido）—— 自架版的 release 監看

**對我的自建——兩個意義** 💭

## 四、組 C：repo 打包 —— 「撞」的引擎零件

動詞鏈裡「**撞**」的前置動作：想法要跟 repo 內容對撞，內容得先變成一包 LLM 吃得下的東西。這一段**完全不用自己寫**——而且兩個工具代表兩種相反的設計哲學，剛好對應我的兩種場景。

### 4.1 Repomix —— 把上下文準備當成正經工程 ⭐

**它是什麼**（標語原文：*Pack your entire codebase into a single AI-friendly file.*）✅
把整個 repo 打包成單一 LLM 友善檔的工具，2025 JSNation 開源獎入圍。核心能力：
- **多格式輸出**：XML／Markdown／JSON／純文字（XML 是給 Claude 的最佳化格式）
- **token 計數**：逐檔＋全庫，打包完直接告訴你這包丟進去要花多少
- **Git 感知**：自動遵守 `.gitignore`
- **Secretlint 洩密掃描**：長得像憑證的檔案自動擋掉
- **Tree-sitter 智慧壓縮**：據稱可省約 70% token——保留程式結構、砍掉實作細節
- **遠端打包**：直接給 GitHub 網址或縮寫就打包，不用先 clone

**設計哲學** 💭
它的立場是：**「餵 LLM」不是 `cat *.py`，是一個有 token 經濟、有安全邊界、有格式工程的正經管線。** 每個功能都對應這個立場的一面——token 計數與壓縮是成本工程、Secretlint 是安全邊界、XML 格式是針對模型的格式工程、MCP server 是讓 agent 自己驅動管線。它把一個大家用殼層指令湊合的動作，升格成一個可依賴的基礎設施。

**技術棧與使用方式** ✅
CLI（npm／yarn／bun／Homebrew 安裝，`npx repomix` 免裝即用）、網頁版、Docker、Chrome 擴充、**MCP server**。**MIT 授權**。

**對我的自建——怎麼接** 💭
1. **碰撞台的「撞」呼叫它的 MCP／CLI 打包**——我選好 repo 組合，打包交給它，我一行打包程式都不寫。
2. **token 計數變成「挑」的預算函數**——「這組 repo 撞下去要花多少」從憑感覺變成可算的數字；「挑要挑多細」由這個數字反推。**這是零件反過來定義我的設計參數的例子。**
3. **Secretlint 天生站在我的公私分界線上**——引擎要開源、資料要私有（護欄 2），打包時的洩密掃描就是那條線的自動哨兵。
4. MIT 授權，抄接皆可，無 AGPL 問題。✅

**它停在哪裡** 💭：**它不知道要打包哪些。**「挑哪幾個 repo、哪幾個檔案」永遠是我的語意層的事——Repomix 是撞的引擎，挑的大腦沒人做。

連結：<https://repomix.com/>

### 4.2 gitingest —— 極簡主義的反面路線

**它是什麼** ✅
把任何 git repo 轉成 LLM 友善文字 digest 的服務。招牌用法：**把 GitHub 網址裡的 `github.com` 換成 `gitingest.com`，立刻得到 digest**——輸出＝摘要＋目錄樹＋完整檔案內容，可複製可下載。另有網頁介面、Chrome 擴充、PyPI 的 Python 套件（可程式化使用）。私有 repo 用 PAT（官方聲明 token 不存後端、clone 完即刪）。單檔上限 50kB。

**設計哲學** 💭
與 Repomix 相反的極簡路線：**一個 URL 改寫就是全部介面**。它犧牲所有進階功能（沒有 token 計數、沒有壓縮、沒有洩密掃描）換取一件事——**啟動摩擦趨近於零**。連「安裝」這個步驟都不存在。兩個工具的對比是一堂完整的設計課：同一個問題（repo → LLM 文字），一個往深做成管線，一個往淺做成反射動作，**而且兩個都是對的，因為服務的場景不同**。

**對我的自建——兩個意義** 💭
1. **捕捉場景的零件**：看到別人的 repo、想立刻丟去撞的那一瞬間（瀏覽器裡、手機上），改四個字就有料。與 Repomix 的分工：**gitingest＝捕捉（別人的、要快），Repomix＝生產（自己的、要壓縮、要算 token、要防洩密、要給 agent 自動跑）**。
2. **「改網址就能用」是啟動摩擦的極致示範**——修正 A 說碰撞台的成敗變數是啟動摩擦（靈感半衰期以分鐘計）。gitingest 證明「零安裝、輸入路徑最短」可以做到什麼程度；**我的碰撞台入口要以這個標準自我要求**，不管載體最後是指令、hotkey 還是手機。

**限制** ✅💭：無 token 計數、無壓縮、無洩密掃描、50kB 單檔上限、走外部服務（私有內容要想清楚）。

連結：<https://gitingest.com/>

## 五、組 D：知識層的兩個對照組 —— 脊椎 schema 照這面鏡子磨

這兩筆 §12 v1 只列在來源行、沒進表格，但它們是 11 個裡**最接近我核心資產（資料脊椎）**的，對自建的貢獻反而最大。

### 5.1 second-brain（NicholasSpisak）—— Karpathy LLM Wiki 模式的開源實作

**它是什麼**（定位句原文：*Drop raw sources into a folder, let the LLM compile them into a structured wiki, and browse it all in Obsidian.*）✅
實作 Andrej Karpathy 的 LLM Wiki 模式的個人知識管理系統：把原始素材丟進資料夾，讓 LLM 把它們編譯成一個結構化、有交叉連結的 wiki，用 Obsidian 瀏覽。vault 結構：

```
your-vault/
├── raw/       # 原始素材收件匣
├── wiki/      # 整理後頁面（sources / entities / concepts / synthesis / index）
├── output/    # 產出報告
└── 設定檔
```

以 `npx skills add NicholasSpisak/second-brain` 一行安裝，得到四個 agent skill：`/second-brain`（vault 初始化精靈）、`/second-brain-ingest`（消化原始素材）、`/second-brain-query`（問 wiki 問題）、`/second-brain-lint`（健康檢查）。走 **Agent Skills 標準**，Claude Code／Cursor／Gemini CLI 等 40+ agent 通用。

**設計哲學** 💭
角色分工講得很清楚：**人當 curator（挑什麼值得進來），LLM 當 librarian（整理成 wiki），Obsidian 當 reader**。更深一層的立場是「**知識庫是編譯產物**」——raw 是 source code，wiki 是 build output，所以理論上可以隨時重編譯；agent 負責維護交叉連結與索引。而 `/second-brain-lint` 的存在透露了誠實的一面：他們知道編譯產物會腐爛，衛生檢查得做成一等公民。

**成熟度**：699 stars／107 forks，維護中。✅

**對我的自建——可抄的設計決策** 💭
1. **`wiki/` 五類頁面的切法（sources／entities／concepts／synthesis／index）**——我在想脊椎欄位怎麼切（開放問題 #4），這裡有一個 699 star 的人切過一版，直接當對照組。
2. **`/second-brain-lint` 的存在本身**——他們也發現「知識庫會爛掉，需要衛生迴圈」，跟我的卡片病史（86 張弱孤兒卡）同病。他的解法是內建 lint skill，我的解法是週復盤＋環境層讓陳舊浮上來——**兩種解法，值得在自己的工具裡驗證哪個活得久**。
3. **用 Agent Skills 標準發佈、`npx skills add` 一行安裝**——等我的引擎到「開源畢業」那天，發佈形態可以照抄。

**它跟我的差異＝我的獨門的精確位置** 💭
它是「raw → LLM 編譯 → wiki」的**單向消化**；我的碰撞台是**雙向代謝**（想法去撞 repo、撞完落回 repo）。它單一 vault、無 registry 概念（沒有「我有哪些牌」這層）、無決策留痕（記知識，不記「我當時選了什麼、依據是什麼」）。

連結：<https://github.com/NicholasSpisak/second-brain>

### 5.2 Iwo Szapar《A Second Brain for Your AI Agents (2026)》＋ MemoryOS —— 抄他的寫入紀律，不抄他的架構

**它是什麼** ✅
一篇論述＋一個產品。論述講的是**多個 agent 共用一層記憶**（不是人的第二大腦，是 agent 們的）：一個 agent 的發現要能被其他 agent 用上。他主張的架構有四個元件：
1. **共用記憶庫**：一個 MCP memory server，裡面放**分型別的**知識集合
2. **MCP 連線**：不同 client（Claude Code／Cursor…）裡的 agent 連同一台 server
3. **統一協定**：所有 agent 遵守同一套「什麼時候該回想、資訊怎麼歸檔」的規則
4. **寫入紀律**：**分型別的紀錄（決策／事實／未結事項）、就地更新而非不斷追加、內建陳舊偵測**

他點名沒有共用記憶的三個病：agent 各自重新發現同一件事、互相衝突的決策沒人發現、**人被迫變成整合層**。產品是 **MemoryOS**：MCP 記憶服務，$199/年、Pro $349/年、另有免費 Health Check；支援 Claude Code／Claude Desktop／Cursor／Windsurf。

**設計哲學** 💭
兩個立場值得記：(1) **記憶是基礎設施，不是單一 agent 的附件**——這跟 openclaw 的「agent 強不強取決於你餵它的記憶結構」是同一條線；(2) **治理比儲存重要**——他花在「寫入紀律」的篇幅比「用什麼存」多，協定與型別才是記憶可信的來源。這第二點我完全同意，第一點的實作方式（外包給 SaaS）我不同意。

**對我的自建——可抄的設計決策** 💭
1. **typed records：決策／事實／open loops（未結事項）**——直接餵開放問題 #4。我的脊椎五類（簡報快照／我的選擇／決策與依據／建議與採納／碰撞記錄）**沒有「未結事項」這一型**，值得補：它正是「儀式 1 早晨簡報」天然要讀的東西。
2. **陳舊偵測（staleness）內建於寫入紀律**——與我「環境層讓陳舊者浮上來」同構，印證這件事要做在資料層、不是做成另一個要去看的報表。
3. 他的三個病裡第三個（**人被迫變成整合層**）就是我現在的日常——可直接用來對外解釋我為什麼要建這個工具。✅💭

**不抄的（本輪查證最有價值的一條）**：

> 他說「**就地更新，不要一直追加**」；我的 §9 說「**脊椎＝append-only**」。
>
> 💭 檢視後確認：**我沒錯，而且我的設計已內建他要解的問題**——因為我拆成兩份資產：`registry`（空間軸、現在為真）**就地更新**；`脊椎`（時間軸、當時發生過）**只能追加**。他把兩件事混在一個 store，才被迫在「新鮮」和「歷史」二選一。而我的北極星（回顧過去的自己、看見品味變好）在他的架構下**根本不可能達成**——就地更新會把「當時的我」覆蓋掉。
>
> **外部最佳實踐與我的設計衝突時，衝突點恰好反證了兩份資產拆法是對的。** 這也跟 PM_Head 的分層判準（`0_portfolio/` 活的真相 vs `5_management/` 定版快照）同構——同一個道理在兩個尺度重複出現。

**反面教材（MemoryOS 本身）** 💭：把核心記憶層外包給年費 SaaS＝把要開源的引擎心臟送人，直接違反護欄 2。**記憶層必須是我自己的純文字資產**（§9 兩份資產的立場再獲一票）。

連結：<https://www.iwoszapar.com/p/second-brain-for-ai-agents>

## 七、我的工具的差異化規格 —— 它們全體不做的四件事

這是本檔最該看的一張表。11 個工具拿我第八節的四條體驗判準逐一打分：

| 工具 | 餘光可見 | 無事不報 | 有行動出口 | 打斷要掙得 |
|---|---|---|---|---|
| gitpane | ❌ 要開 TUI「前往」 | ❌ 全量攤開 | ⭕ 可直接 push/pull | －不打斷 |
| mani | ❌ 要下指令 | ❌ 全量 | ❌ 只印結果 | －不打斷 |
| GitKraken Workspaces | △ 桌面常駐算半個 | ❌ 全量 | ⭕ 批次操作 | ❌ 全推 |
| GitHub Repo Dashboard 🔗 | ❌ 要開網頁 | ❌ 全量 | △ | －不打斷 |
| **NewReleases.io** | **⭕ 推到我已在的地方** | **⭕ 沒新版就沉默** | ❌ 只給連結 | △ 可設每日彙整 |
| github-release-monitor | ⭕ Apprise 推播 | ⭕ | ❌ | △ |
| Repomix／gitingest | －非監控類 | － | － | － |

💭 從這張表**反向讀出我的工具的四條規格**：

1. **監控層長得像通知系統，不像儀表板。** 儀表板類四個全是「要前往的頁面」——跟我 `repo-healthcheck` 同一個死因。（**2026-09-01 裁定修訂**：監控台**要做**，判準管的是**預設體驗**——預設面只呈現異常與變化、自帶行動出口；「把當前狀態全量攤開」降為可主動開啟的「深看模式」，不得是預設面。）
2. **通知自帶行動出口。** 連通過前兩條的 release 類都掛在這條——沒有一個現成品會在通知底下附「一鍵進 inbox」「一鍵開碰撞」。**通知與行動之間那一公分，就是我的工具的護城河的精確位置**：那是「落」與「撞」接上訊號的地方。
3. **打斷要自己掙得。** 沒有任何工具對「該不該現在打擾我」有模型（素材檔 §3.8-7 印證：全產業都用 if-this-then-that）。我的體驗層有四個場合可依附——不可逆／賠不起／沒把握才打斷，其餘進未讀等儀式時刻。
4. **懂場合。** 「什麼時候、以什麼形式出現在眼前」取決於我的四個場合——這是任何通用工具原理上不可能知道的事，也是體驗層必須自建的根本原因（§8 的策略切分再獲實證）。

## 九、餵設計決策的三個實驗（各 15–30 分鐘，都不寫程式）

不是採購試用，是**用最便宜的方式把設計參數量出來**：

| # | 做什麼 | 量出哪個設計參數 |
|---|---|---|
| 1 | `tool_experiments` 那批 repo 貼進 **NewReleases.io**，設每日彙整推到我已在的地方 | 訊號源零件的可用性＋親身體感「無事不報」→ 監控層第一版的形態基準 |
| 2 | **`npx repomix`** 對一組真實 repo 組合跑一次 | 「一次能撞多大」的 token 數 → **「挑」的粒度直接由這個數字反推** |
| 3 | 開一次 **GitHub 官方 Repository Dashboard** | 我的工具可以**不做**的範圍邊界 |

### 讀（不裝），各 20–30 分鐘，餵開放問題

- **mani 的 `mani.yaml`** → registry 超集夠不夠用（開放問題 #3）
- **second-brain 的 `wiki/` 五類＋`/second-brain-lint` 檢查項** → 脊椎 schema 對照（開放問題 #4）
- **Iwo Szapar 那篇** → 脊椎要不要補 open loops 一型（開放問題 #4）

### 明確不做

- ❌ 不裝 gitpane／mani／GitKraken 當監控（§7 規格一：外部儀表板過不了四條判準；自建監控台則依 2026-09-01 裁定——預設面過判準、全量檢視為深看模式）
- ❌ Release Detector MCP（已封存；只留形態課）
- ❌ MemoryOS（核心記憶層外包＝違反護欄 2）
- ❌ 現階段不自架 github-release-monitor（先用 SaaS 量需求；要接也是服務級，AGPL 不抄 code）
