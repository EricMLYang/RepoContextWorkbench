# 工作台 UX 與 Agent 角色檢討

日期：2026-09-12。檢視版本：`b024c5c`。

性質：資深 UX 設計師角度的體驗檢討與改善建議。本文記錄觀察、推論、優先序與驗收方向；建議尚未實作，不取代現行規格或先前落地記錄。

## 1. 核心判斷與檢視範圍

作品已有清楚的工作台骨架，但「幫使用者重新進入工作、判斷下一步、持續接手」的體驗還沒串完整。Agent 已取得組的脈絡，介面尚未充分呈現它的理解與責任。

本次對照目前程式碼、既有設計紀錄，並以獨立暫存 spine 啟動瀏覽器工作台。示範資料包含三個假 git repo（產品規劃、產品實作、研究筆記）、兩組（產品開發、知識研究）、一條 PM 關係，以及一筆屬於產品開發的到期待辦。實際查看首屏、切組、關係頁及 Agent 開場表單；簡報範圍問題另以 Python 函式直接呼叫確認。

沒有啟動真實模型會話、使用正式 spine、修改產品程式，亦未執行真實使用者測試、Windows/VDI 原生視窗測試、完整無障礙稽核或長時間觀察。示範情境不能用來推論真實專案的工作優先序。會話執行與交接的評估以程式碼為依據。

## 2. 值得保留的基礎

- **以組為工作單位**：規劃、實作、研究可以放在同一個範圍理解，符合跨 repo 的工作方式。
- **清楚的工作台結構**：工作範圍、待處理／Repo／活動／關係四個分頁、卡片主次與可收合終端，已形成可延伸的骨架。
- **Agent 的開場脈絡**：組情境卡已包含成員、關係、活動、未結事項與來源要求，能減少重講背景的成本。
- **既有可信操作**：前輪已補上的草稿保留、斷線提示、範圍標示及動作留痕應繼續保留；本輪不把已修正的缺口重新列為現況。

程式依據：[context.py](../repo_context/context.py) 的 `ROLE_PROMPT`、`build_context()`；[workbench.html](../repo_context/workbench.html)；前輪證據見 [成熟度檢討落地記錄](20260908_工作台UI_UX成熟度檢討_落地記錄.md)。

## 3. 首頁：從狀態數量走向工作脈絡

**觀察：** 頁首回答有幾個 repo、幾件待處理；卡片回答哪些規則被觸發。使用者仍需自行還原「上次做到哪裡、哪些變化影響原本的工作、現在值得接著做什麼」。

示範首屏將「產品實作 28 天無 commit」放在「確認規劃與實作的驗收條件是否一致」之前，前者主要動作是「降 tier」。這證明目前排序與主要動作容易讓維護登記狀態取得較強的視覺優先權；兩件事是否有因果關係仍需查證。

**建議：** 在卡片前加入簡短的「本組工作摘要」，呈現目前目標、上次進度、重要變化與可接續的一步。摘要附來源與更新時間；資訊不足時直接說明，不能把 commit 數當成進度或價值。目標可先由使用者提供一句話，避免為此增加大量設定負擔。

卡片主要動作應由使用者要完成的工作與證據決定。「長時間未提交」可以先提供查看變化或釐清狀態的入口；調整 tier 保留為明確選項。

程式依據：[workbench.js](../repo_context/static/workbench.js) 的 `renderHeader()`、`renderCards()`、`primaryAction()`；[brief.py](../repo_context/brief.py) 的 `build_question_cards()`。

## 4. Agent：把組管家變成可理解的服務

**觀察：** 開場表單主要提供 Agent 選擇與任務輸入；預設任務是「先讀情境卡，用 3 行告訴我這組現況（活動、異常、未結），再問我要做什麼」。背景準備已有改善，任務形成與推進仍主要靠使用者。

**建議角色：** 組管家負責跨 repo 的脈絡整理、問題釐清與工作交接。以下是同一個 Agent 在不同階段的責任，不需要因此拆成多個 Agent。

| 時機 | Agent 應負責 | 使用者應看見 |
| --- | --- | --- |
| 進入工作組 | 整理變化、接回上次工作 | 現況、來源、可繼續的任務 |
| 出現問題 | 比對相關 repo、辨認缺漏 | 判斷理由、未知處、建議下一步 |
| 執行任務 | 在約定範圍內工作、回報阻塞 | 正在處理什麼、是否需要使用者回應 |
| 結束工作 | 整理成果與未完成事項 | 可檢閱的成果、下次接續點 |

開場應簡短呈現它拿到哪些脈絡、這次預計產出什麼，以及哪些動作需要再確認。保留自由輸入，同時提供有情境的入口，例如「接續上次工作」或「檢查規劃與實作是否一致」。

目前「不越組」主要寫在角色指令中，不能把畫面上的工作範圍宣稱為已強制限制的工具權限。設計上應清楚區分範圍、行為約定與實際權限；執行能力及確認點依使用者已授權的任務決定。

程式依據：[context.py](../repo_context/context.py) 的 `ROLE_PROMPT`；[session.py](../repo_context/session.py) 的 `DEFAULT_TASK`、`build()`；[workbench.js](../repo_context/static/workbench.js) 的 `openSession()`；[mcpserver.py](../repo_context/mcpserver.py) 的工具入口。

## 5. 會話：讓工作能接續

**程式碼觀察：** 會話清單主要以程序是否存活呈現「執行中／已結束」。使用者需要的狀態則包括正在處理、等待回答、遇到阻塞與已有成果。程序存活不足以代表工作正在推進。

「記錄結果」仍是需要手動填寫的空白表單。Agent 雖被要求自行留痕，介面尚未穩定呈現成果交接，使用者仍可能要自己整理終端內容。本次未以真 Agent 驗證此流程。

**建議：** 讓 Agent 產生可編輯的交接草稿，包含成果連結、重要判斷與剩餘事項，並能辨認哪些已儲存、哪些仍待確認。下次進入同組時提供「接續上次工作」。保留終端，同時增加任務摘要作為日常入口。

任務狀態應有可追查的依據；Agent 無回報或連線中斷時顯示未知／中斷，不能只根據程序存活推定進度。成果紀錄也應維持既有語意：記錄 decision 不等於證明想法已被採納或產生 outcome。

程式依據：[workbench.js](../repo_context/static/workbench.js) 的 `syncTerms()`、`sessionResult()`；[webui.py](../repo_context/webui.py) 的 `session_result` action。

## 6. 優先修正兩個信任問題

### 6.1 「本週排進度」實際只延後提醒

**原始碼確認：** `build_question_cards()` 中，該按鈕呼叫 `defer`，參數為 `days=7`，沒有建立進度安排。本次未點擊該動作。

**影響：** 使用者可能以為系統已安排工作，實際只暫時看不到提醒。

**建議：** 若保留現有行為，改名「七天後再提醒」；若保留安排進度的文案，需提供真正的排程／任務建立流程及結果回饋。

**驗收：** 按鈕文字、執行效果、成功提示與活動紀錄一致，使用者能說明系統究竟做了什麼。

### 6.2 組別簡報混入其他組的待辦

**已以函式呼叫重現：** 暫存 spine 只有一筆屬於「產品開發」的到期待辦，直接呼叫 `build_brief(spine, "知識研究", [])`，產出的「知識研究」簡報仍包含「確認規劃與實作的驗收條件是否一致」。空狀態列表用來隔離未結事項的範圍問題；本次未從 UI 點擊儲存簡報。

**原因：** [brief.py](../repo_context/brief.py) 的 `build_brief()` 直接取 `spine.open_loops(spine_dir)`，沒有依工作組篩選未結事項。

**影響：** 介面宣告的組別與內容不一致，可能讓使用者或 Agent 把其他組的任務當成當前責任。

**建議：** 簡報沿用一致的範圍判定。組內事項依所選組過濾；全域或未分類事項若需保留，獨立標示。另確認簡報的靜默文案只陳述採集能支持的結果，避免「無變化」超出提醒閾值的證據。

**驗收：** 兩組各有到期與新增待辦時，本組簡報只包含本組事項；臨時組、全域與未分類情境亦有明確規則。畫面、簡報與 Agent 開場脈絡的歸屬應一致。

## 7. 降低設定成本，讓關係產生立即回報

**觀察：** 關係頁已能讀出「產品規劃 規劃（PM）→ 產品實作」，關係也會進入 Agent 情境。但設定之後能改善哪些工作，介面呈現仍有限。

**建議：** 在關係旁提供具體用途，例如「檢查規劃與實作是否一致」，使關係成為工作入口。Agent 可提出關係建議，但需附依據，讓使用者容易修正。

**首次使用的程式碼觀察：** 未登記 repo 時，空狀態要求先用 `registry add` 或 `registry scan`，再回來更新。對熟悉 CLI 的個人使用者仍增加安裝與加入專案的步驟。

**建議首次流程：** 選資料夾 → 預覽 repo → 建第一組 → 看第一次摘要。先讓使用者得到一次價值，再逐步補關係與其他設定。

程式依據：[workbench.js](../repo_context/static/workbench.js) 的 `renderCards()` 空狀態、關係介面；[context.py](../repo_context/context.py) 的成員關係彙整。

## 8. 視覺與文案調整

目前層級與風格已能支撐使用。後續可改善大螢幕下卡片過寬、動作分散，以及 `tier`、`active`、`dirty` 等內部術語。調整時以清楚閱讀與理解行動後果為準，避免增加純裝飾資訊。

主要設計資源優先投入工作連續性；本輪沒有重新執行字級、對比或觸控目標的量測，不宣稱完整視覺或無障礙驗證。

## 9. 建議落地順序與驗收

以下 P0/P1/P2 表示本輪建議優先序，尚未實作。

| 優先序 | 範圍 | 完成標準 |
| --- | --- | --- |
| P0 | 行動文案與簡報範圍 | 「本週排進度」語意符合行為；組別簡報不再混入其他組待辦 |
| P1 | 一條完整的工作接續流程 | 進入一組 → 理解現況 → 接續一件事 → 檢閱成果 → 留下下次接續點 |
| P1 | Agent 角色與任務狀態 | 使用者知道 Agent 掌握的脈絡、預期產出、目前階段及是否需要自己回應 |
| P2 | 關係的工作入口、首次設定、視覺文案 | 設定關係能直接啟動有用工作；首次建組可在介面完成；操作文案可理解 |

以兩組具有不同工作內容的真實資料驗收，觀察以下行為；這些是建議目標，尚無測量結果：

1. **恢復脈絡**：進入一組後，能否在半分鐘內說出正在做什麼、哪件事值得接著做，以及理由來自哪裡。
2. **減少重講背景**：啟動任務時，需要補述多少已存在於組情境或上次紀錄的資訊。
3. **辨識責任**：Agent 等待、執行、阻塞時，能否判斷現在輪到誰採取行動。
4. **隔日接續**：隔天能否從成果與下一步直接接回工作，無須翻找整段終端內容。
5. **維持信任**：能否正確預期按鈕效果，並辨認內容與行動影響的工作範圍。

這些指標比卡片數量或開啟會話次數更能反映 Agent 是否減少工作負擔。
