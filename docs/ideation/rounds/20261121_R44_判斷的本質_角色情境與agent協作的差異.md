# R44｜2026-11-21｜判斷放在哪裡：agent 協作工具的地圖，與本 repo 的方向

> 標記：✅ 讀過原文（多半是節錄）｜🔗 只看到搜尋結果｜📊 本機 spine 與會話紀錄的回測｜💭 推論。沒標的句子是推論。

## 問題

agent 讓產出變便宜之後，人的判斷變成瓶頸。判斷的本質是什麼？它在人的組織裡和在跟 agent 協作時差在哪裡？
由此該用什麼維度看這一類協作工具？本 repo 在這張圖上的哪裡，該往哪裡走？

## 期望

對工具的定位和方向有一張清楚的地圖，並找到一條之後可以持續進化的方向。

## 結論

**地圖**：用九條有刻度的維度量這類工具（定義見第五節）。20 個外部工具與本 repo 打完分之後：

- 外面的高分集中在四條：監督模式、並行規模、後果圍堵、驗證主體。也就是跑得多、放得開、圍得住、機器先審。
- 三條維度的最高一級沒有任何工具到達：意圖釐清（對著樣板改並把標準收下來）、驗證主體（人只抽查）、回饋吸收（回頭看結果並修正）。
- 官方 App 在九條裡有五條到 3 以上，執行台這一塊正在被它收掉。

**趨勢**：從十一個痛點和為它們長出來的工具歸納，有兩條最要緊的規律。
一是痛會一段一段往後移：先是跑不起來，再是顧不過來、審不完，然後才是講不清楚、看不懂。
二是每個痛都走同一條路：人先硬撐，接著有人做工具，最後變成平台內建。跟機器有關的痛已經走完，跟人有關的才剛開始。

**定位**：本 repo 的刻度組合是脈絡範圍 3、留存深度 4、工作類型廣度 2，表上沒有第二個工具同時有這三項。
它的意思是：別的工具以 agent 的執行單位（一場會話、一個任務）為中心，本 repo 以下判斷的那個人為中心。
多 repo 是這個定位的結果。本 repo 最低的兩條是意圖釐清 0 和驗證主體 1。
這個位置有期限：跨專案的記憶是下一批會被平台內建的東西。

**方向**：沿著判斷的生命線，把四條維度各往上推，順序是驗收、標準、回顧。

| 步 | 做什麼 | 刻度怎麼動 |
|---|---|---|
| 1 驗收 | 所有 repo 等人看、聽、測的事排成一個佇列，附好證據 | 驗證主體 1 → 2，監督模式 2 → 3 |
| 2 標準 | 從每次驗收把改出來的標準與給出的授權收下來，帶到下一次、下一個 repo | 意圖釐清 0 → 4 |
| 3 回顧 | 挑後果大的判斷回頭看結果，看自己的標準怎麼變 | 回饋吸收 3 → 4 |

第 1 步解的是量到的痛點（等人的事 78% 是驗收）。第 2、3 步到達的是目前沒有工具站的刻度，其中第 3 步就是 VISION 的北極星。
每一步用的是上一步留下的資料，所以這條路可以一直走。不該再投資的是並行規模，以及用搜尋與推薦帶案情。

## 推導

### 一、起點：為什麼判斷變成問題

產出變便宜，人就平行跑更多 agent。平行沒有移除瓶頸，只是把成果堆在人面前。

| 量到什麼 | 依據 |
|---|---|
| 655 家公司：程式碼產出大增，最終軟體產出幾乎沒變，審查成為瓶頸 | ✅ Chen 與 Stratton |
| 權限詢問有 93% 被按同意 | ✅ Anthropic |
| 熟手從逐步核准改成放手跑、出事才打斷：全自動核准的會話從約 20% 升到超過 40%，打斷從約 5% 升到約 9% | ✅ Anthropic |
| agent 的動作只有 0.8% 看起來不可逆 | ✅ Anthropic |
| 能做的任務長度約每 3.6 個月翻倍；但在沒有明確回饋就要做選擇的任務上，判斷仍比人類專家差 | ✅ METR |

所以問題從「怎麼做更多」變成「人的判斷該放在哪裡」。要回答它，得先講清楚判斷是什麼。

### 二、判斷是什麼

**定義**：判斷是規則用完之後剩下的東西。

| 出處 | 說了什麼 |
|---|---|
| 康德 🔗 | 規則的適用不能再靠規則，所以任何一套規則都會留下判斷 |
| Agrawal、Gans、Goldfarb 🔗 | 預測告訴你情況是什麼，判斷決定每種結果值多少。預測變便宜，判斷變值錢 |
| Jensen 與 Meckling 🔗 | 決定權要放在知識所在的地方，因為有些知識搬起來很貴 |

**判斷做三件事，各需要一樣原料，另外需要一個人**：

| 成分 | 做什麼 | 需要 |
|---|---|---|
| 歸類 | 這是哪種情況、哪條規則適用 | 案情：這件事的具體知識與證據 |
| 權衡 | 哪個結果比較值得 | 標準：要什麼、在意什麼、規矩、品味 |
| 承擔 | 資訊不夠時定下來，出事時出面 | 紀錄：誰接受了什麼、後來怎樣 |
| | | 一個還懂這件事的人 |

**判斷有一條生命線**：

| 階段 | 發生什麼 |
|---|---|
| 形成 | 標準還不存在，對著問題或樣板把它弄清楚 |
| 寫下 | 標準被凍結成規格、檢查、規則或授權 |
| 套用 | agent 或人拿標準去處理一件一件的事 |
| 驗收 | 看結果對不對 |
| 回顧 | 過一段時間看當初對不對，回頭改標準 |

判斷不會消失，只會在這條線上搬家。把它寫成規則之後，判斷就搬到「這條規則適不適用」和「驗收」。
實證上，56% 的初始指示漏掉後來必要的需求；規格不完整時，模型成功率掉 53 到 67 個百分點（✅ arXiv 2610.17757）。

**不是判斷、但常被混在一起的**：

| | 是什麼 | 怎麼處理 |
|---|---|---|
| 推論 | 從已給的目標與事實推得出答案 | 交出去 |
| 機器做得了的檢查 | 對錯有機制驗得出來 | 交出去 |
| 只有人做得了的檢查 | 對錯明確，但要人的耳朵、手、實機或真實使用者 | 不需要判斷力，卻暫時交不出去 |
| 核准 | 答案事先猜得到的同意 | 變成規則 |

**哪些留給人**：從上面給的目標推不出來，下面的機制也驗不出對錯。每件事問兩個問題就知道怎麼處理：

| 對錯誰驗得出來 | 答案推得出來 | 答案推不出來 |
|---|---|---|
| 機器 | 全交 | 先做幾個，人挑 |
| 只有人 | 交出去做，攢成一批給人驗 | 人對著一個樣板來回改，改定後移到左邊 |
| 只有時間 | 做，記下當時的判斷，之後回顧 | 人事前判斷，並記下理由 |

不管落在哪一格，對外、收不回來、碰到真實使用者或資料、會留下還在跑的東西，都先停下來。

所以判斷需要四樣東西、走一條五段的線。接下來要看：交給 agent 時，這四樣東西和這條線哪裡斷掉。

### 三、人的組織和 agent 協作差在哪

**一句話**：在人的組織裡，任務、知識、責任、感官一起往下放；交給 agent 時只有任務下去。

| 面向 | 人的組織 | 跟 agent 協作 | 依據 |
|---|---|---|---|
| 知識 | 部屬久了會累積在地知識 | 一般知識極多，在地知識每次從零開始 | 🔗 |
| 責任 | 部屬承擔後果 | 不承擔。把 AI 稱為「員工」時，主管抓到的錯少 17%，並把責任推向 AI | ✅ Wiles 等 |
| 感官與操作 | 部屬自己會聽、會看、會拿真機測 | 聽不到聲音、碰不到實機與真實使用者 | 📊 |
| 反對意見 | 部屬會反對、會提醒 | 傾向同意。使用者最常遇到的失敗是「順著你說」 | ✅ 2610.34748 |
| 過濾層 | 每一層替上一層擋掉大部分判斷 | 一個人直接對很多 agent | ✅ Chen 與 Stratton |
| 成本 | 做很貴，所以先想清楚再做 | 做和重做都便宜，變成先做一個、對著它改 | 📊 |
| 意圖 | 沒講的靠共同文化補上 | 沒講的用一般常識補，得到平均值 | ✅ 2610.17757 |
| 回報 | 摘要可信、可以追究 | 只看報告只答得出 52% 的狀態問題，直接問 agent 答得出 93.6% | ✅ 2610.20003 |
| 信任 | 跟著人累積 | 跟著模型與任務類型，換版本要重估；最嚴重的失敗最難察覺 | ✅ 2610.34748 |
| 能力 | 交辦同時在養人 | 沒有人被養到，交辦的人還可能退步 | 🔗 Shen 與 Tamkin |

**各角色留什麼、放什麼**。共同結構是每一層的判斷變成下一層的限制。

| 角色 | 留 | 放 | 交給 agent 後多出來的事 |
|---|---|---|---|
| 老闆 | 賭哪幾件事、不做什麼、能輸多少 | 怎麼做 | 「做得到」不再替你過濾點子，「不做什麼」更值錢 |
| 部門主管 | 誰負責什麼、品質底線、資源給誰 | 個別任務的做法 | 審查的人力要編預算；哪些事為了養人必須由人做 |
| PM | 哪個問題值得解、什麼叫做完、先後 | 規格細節 | 樣板與例子比敘述重要 |
| 專案管理 | 對外承諾、哪個風險會咬人、何時砍範圍 | 狀態追蹤 | 關鍵路徑變成等人驗收 |
| 架構師 | 改起來貴的東西、不變的規則 | 介面後面的實作 | 把規則寫成機器驗得出來的檢查 |
| 設計師 | 該是什麼感覺、哪個對、為什麼 | 產生變體 | 從先講清楚變成做一個再改 |
| 工程師 | 問題是什麼、什麼叫正確、哪 5% 親自看 | 多數實作與逐行審查 | 機器測不到的地方要人動手 |
| 研究與知識工作 | 哪個問題值得問、什麼算證據 | 蒐集與整理 | 對錯機器驗不出來，正是 agent 最弱的地方 |

所以交給 agent 之後，留在人身上的有四樣：在地知識、責任、感官、理解。理論講到這裡，下一步看實際上人被什麼佔住。

### 四、實際上人在做什麼

資料是本機的 spine 與會話紀錄（📊）：322 筆交接裡逐筆讀了最近 70 筆（11-13 至 11-21，四個 repo），加上近 14 天的健康指標與 114 場會話紀錄。

**agent 在等人什麼**（70 筆裡 51 筆在等人）：

| 類型 | 筆數 | 佔比 |
|---|---|---|
| 看、聽、讀成果，給回饋 | 25 | 49% |
| 實機或人工測試 | 15 | 29% |
| 定方向、定範圍 | 5 | 10% |
| 補只有人知道的內容 | 3 | 6% |
| 單純等 commit 或 push | 3 | 6% |

**六個發現**：

1. **人的判斷多半發生在看到東西之後。** 「看了才說哪裡不對」是「先決定走哪邊」的五倍。
2. **跨天堆著的是要人動手的檢查，不是決定。** 看成果的 25 筆有 15 筆是即時來回；堆著沒做的是人工測試。
3. **標準是對著樣板改出來的。** 一支動畫樣板 34 分鐘內來回 6 次，定下來後寫成規格與自動檢查，加一個監督 agent，後面一百多支就不再問。
4. **授權在對話裡給，單位是任務。** 「後面都不用問，除了 push 和動別的 repo；一次幾個、檢查多嚴我當次說。」
   工具的決策卡 14 天只收到 1 筆回答，放行規則 0 條。
5. **事故都落在真實使用者身上。** 找到兩件：開了伺服器兩天沒關、測試資料混進小孩的進度。agent 都不是沒把握。
6. **跨 repo 參考是常態，但靠指路。** 14 天至少 114 次跨 repo 讀取，都是使用者指路或開場給路徑後直接讀；經過工具的只有 8 次。

另外，commit 看起來是驗收章而不是風險閘門：提到 commit 的 21 筆有 18 筆綁著「看過才 commit」。這是推論，沒有跟使用者確認。

所以實際的瓶頸在生命線的後段（驗收），關鍵時刻在前段（標準形成），而兩段工具都沒有參與。有了這些，可以回頭定評估工具的維度。

### 五、地圖：九條維度

把第二節的生命線和第三節留在人身上的東西對起來，得到九條可以用刻度量的維度。生命線的每一段都有對應的尺：

| 生命線 | 維度 |
|---|---|
| 形成 | 意圖釐清 |
| 寫下 | 留存深度 |
| 套用 | 監督模式、並行規模、後果圍堵 |
| 驗收 | 驗證主體 |
| 回顧 | 回饋吸收 |
| 整體 | 脈絡範圍、工作類型廣度 |

**維度與刻度**

1. **Context Scope（脈絡範圍）**：系統維持連續脈絡的單位。
   0 Session 一場會話｜1 Task 一個任務｜2 Repository 一個 repo｜3 Cross-repository 一個人的多個 repo｜4 Team 團隊
2. **Persistence Depth（留存深度）**：跨越會話與 repo 邊界後仍可取得的內容層次。
   0 None 不留｜1 State 狀態（誰在跑、誰在等）｜2 Artifacts 檔案與脈絡｜3 Norms 規矩與標準｜4 Decisions & Outcomes 判斷紀錄與後來的結果
3. **Intent Elicitation（意圖釐清）**：動工前，系統幫人把要什麼、什麼算好弄清楚的程度。
   0 Prompt as Given 照指示直接做｜1 Plan Proposal 先提計畫給人看｜2 Clarifying Interview 逐題問到沒有模糊｜3 Structured Specification 寫成規格與驗收條件｜4 Exemplar-driven Refinement 對著樣板來回改，並把改出來的標準收下來
4. **Oversight Mode（監督模式）**：人介入 agent 執行的時機與密度。
   0 Per-action Approval 逐步核准｜1 Synchronous Turn-taking 即時輪流來回｜2 Monitoring with Interruption 看著它跑，出事才打斷｜3 Post-hoc Batch Review 做完後成批驗收｜4 Exception-based Oversight 只處理例外
5. **Agent Concurrency（並行規模）**：設計上讓一個人同時運行的 agent 數量，以及靠什麼協調。
   0 Single 單一 agent｜1 Few, Manually Switched 兩三個，人手動切換｜2 Several with Status Overview 五個左右，有狀態總覽｜3 Many with Orchestration 十個以上，由 agent 派工｜4 Fleet 數十個以上的車隊
6. **Consequence Containment（後果圍堵）**：系統限制錯誤動作影響範圍的強度。
   0 None 沒有限制｜1 Per-action Prompt 每次動作前詢問｜2 Rule- or Classifier-based Gate 用規則或分類器把關｜3 Workspace Isolation 工作區隔離（worktree）｜4 Sandboxed Environment 沙盒環境
7. **Verification Locus（驗證主體）**：產出的正確性由誰、依據什麼先行判定。
   0 Human on Raw Output 人看原始輸出｜1 Human on Structured Diff 人看整理好的差異｜2 Human with Evidence Artifacts 附上證據給人看｜3 Machine- or Agent-first Review 機器或另一個 agent 先審｜4 Human Spot-check 人只抽查
8. **Feedback Incorporation（回饋吸收）**：人的回饋被保留並影響後續行為的程度。
   0 None 用完就忘｜1 Transcript Logging 留對話紀錄｜2 Manually Authored Rules 人手寫規則｜3 Automated Memory Consolidation 自動整理成記憶或紀錄｜4 Outcome-based Refinement 回頭看結果並修正做法
9. **Work Domain Breadth（工作類型廣度）**：系統假設的工作內容。只有三級。
   0 Code Only 只有程式｜1 Code and Docs 程式加文件｜2 Any File-based Work 任何以檔案為主的工作（知識、簡報、內容）

名稱仿照人機協作綜述（arXiv 2505.00753 ✅ 部分）的寫法，但多數是我取的。對得上該論文原有術語的只有兩條：
監督模式對應它的 Temporal Synchronization 與 Feedback Phase，回饋吸收對應 Feedback Phase 的事後階段。
脈絡範圍、留存深度、並行規模沒有那篇論文可以掛；並行規模的依據是 R43 的實務文章。

### 六、趨勢：從痛點和工具的對應歸納

做法是歸納：先列現在看得到的痛點，以及為它長出來的工具，再看這些個案有沒有共同的走法。
個案取自 R43 整理的九個趨勢和這一輪的搜尋。

**看到的個案**

| # | 現在的痛 | 依據 | 為它長出來的工具 | 現在走到哪 |
|---|---|---|---|---|

| 2 | 不知道誰在等我、視窗一關就斷 | R43 | 狀態側欄、會話常駐、OSC 7501 | 已經是協定：六週內 41 個程式有 21 個支援（✅ R43） |

**從個案歸納出的五條規律**

**一、痛是一段一段往後移的。**
先痛的是跑不起來、撞在一起。跑順了，才發現顧不過來。顧得來了，才發現審不完。審得動了，才發現一開始就沒講清楚。
最後才發現，人自己已經看不懂了。這個順序就是第二節那條生命線：先是套用，再是驗收，然後回頭補形成，最後才輪到回顧和人本身。

**二、每個痛都走同一條路：人先硬撐，接著有人做工具，最後變成內建。**

| 痛 | 人硬撐 | 有人做工具 | 變成內建或協定 |
|---|---|---|---|
| 權限 | 每次按同意 | 規則與核准工具 | auto mode |
| 狀態 | 自己切過去看 | 各家讀畫面或掛 hook | OSC 7501 |
| 記憶 | 重講一次 | 記憶外掛 | 內建記憶 |
| 規矩 | 每個工具各寫一份 | 規則同步 | AGENTS.md 成為通用格式 |
| 審查 | 自己讀 diff | AI 審查工具 | 平台開始內建 |

十一個個案裡，前七個已經走到最後一步或正在進去，後四個還在前兩步。
走得快的只花幾週（狀態協定），慢的大約一年。做出來的 App 會被收掉，留下來的是格式與協定。

**三、工具都在幫人離開現場。**
規格和規矩是讓人事前講好就走，審查和紀錄是讓人事後再回來看。幾乎沒有工具是要人當下盯得更緊。

**四、一開始都往多衝，後來都退回剛好。**
平行開越多越好，後來實務上限落在三到五個。編排框架越做越大，後來退回「開一個、傳話、等回報」三個小指令。
脈絡檔越寫越多，後來研究發現寫多了成功率反而下降（以上皆 R43）。數量先被當成賣點，接著被驗證卡住，然後收斂。

**五、越是機器的問題越快有解，越是人的問題越沒人解。**
agent 怎麼跑、怎麼圍、怎麼記，都已經內建。人講不清楚、人看不懂、誰負責，還停在技巧和提案。

**由此看接下來**

1. **下一批變成內建的**，是現在第三方做得最熱的：AI 審查、跨專案的記憶、多 repo 的工作區。
2. **下一批長出成熟工具的**，是現在靠自己做或靠技巧的：動工前的釐清、跨 repo 的脈絡與規矩。
3. **最後才會有的**，是現在只有提案的：讓人繼續懂自己的系統、回頭看當初判斷得對不對。
4. **數量不再是賣點。** 能同時開幾個、脈絡能塞多少，都會往「剛好」收，比的會是驗收和釐清。

用九條維度來說：後果圍堵、監督模式、並行規模的高分已經是標配；驗證主體是現在的戰場；
意圖釐清和回饋吸收的最高一級，是最晚才會有人到的地方。

### 七、本 repo 在圖上的哪裡

**單位不同**。別的工具繞著 agent 的執行單位組織，本 repo 繞著人組織（一手牌是一組 repo）。
實際在跨 repo 的四樣東西都跟著人走：案情（14 天至少 114 次跨 repo 讀取）、注意力（四個 repo 交錯等人）、
規矩（同樣的規矩在每個 repo 重複）、判斷紀錄（spine）。

**九條維度的現況**（📊）：

| 維度 | 刻度 | 實際狀況 |
|---|---|---|
| 脈絡範圍 | 3 一個人的多個 repo | 有在用：跨 repo 讀取靠開場給的路徑與使用者指路 |
| 留存深度 | 4 判斷紀錄與結果 | 14 天 92 次交接；但紀錄 77% 是 agent 寫的，結果只記了 4 筆，人的規矩沒收到 |
| 意圖釐清 | 0 照指示直接做 | 樣板來回發生在對話裡，工具沒參與 |
| 監督模式 | 2 看著、出事才打斷 | 有會話列與等人的標記；決策卡 14 天只回答 1 張 |
| 並行規模 | 2 有狀態總覽 | 執行台都更強，不該追 |
| 後果圍堵 | 3 工作區隔離 | 有 worktree 隔離，寫別組會被拒；放行規則 0 條 |
| 驗證主體 | 1 人看差異 | 等人的事 78% 是驗收，都由人做；總管還在試 |
| 回饋吸收 | 3 自動整理成紀錄 | 交接與判斷自動留痕；回頭看結果的功能有，沒在發生（推薦 103 次用上 0 次） |
| 工作類型廣度 | 2 任何檔案工作 | 程式、知識卡片、簡報、給小孩的產品 |

**高分的兩條還分不分得開**。脈絡範圍 3 和留存深度 4 的組合是獨有的，但拆開來每一格都有人在做：

| 跨 repo 帶什麼 | 外面誰在做 | 本 repo 還分得開的地方 |
|---|---|---|
| 檔案與脈絡 | 團隊自建的登記表與相依圖、Home Repo Pattern | 幾乎沒有 |
| 規矩與標準 | 至少五個規則同步工具；平台的使用者層設定檔 | 只剩「對話裡給的任務授權」沒人收 |
| 判斷紀錄 | 記憶工具多半以專案為界；會話搜尋是未整理的逐字稿 | 跨 repo 的判斷時間軸，沒找到別人做 |
| 等人驗收的事 | 核准佇列管的是事前核准；執行台只有狀態 | 以人為單位排驗收，沒找到別人做 |

所以定位是：以人為單位的判斷層。獨有的是刻度的組合，不是任何單一格子；最低的兩條（意圖釐清、驗證主體）正好是回測裡的關鍵時刻與痛點。

**這個位置有期限。** 第六節歸納出來，跨專案的記憶和多 repo 的工作區是下一批會被平台內建的。
到那時，脈絡範圍 3 加留存深度 4 的組合就不再獨有。

### 八、方向：沿著判斷的生命線往上推

把第四節的痛點、第五節的空白、第六節的趨勢、第七節的低分疊起來，得到一條有先後的路：

| 步 | 做什麼 | 刻度怎麼動 | 為什麼排這裡 | 怎麼知道有用 |
|---|---|---|---|---|
| 1 | 驗收佇列：所有 repo 等人看、聽、測的事排在一起，照需要的環境分批，附好證據，結果留痕 | 驗證主體 1 → 2；監督模式 2 → 3 | 量到的痛點；沒找到別人以人為單位做 | 交接到驗收的等待時間變短 |
| 2 | 從驗收收標準：樣板定下來時，把改出來的標準與給出的授權記下，帶到下一次與下一個 repo | 意圖釐清 0 → 4 | 用第 1 步的資料；這是交出判斷的關鍵時刻 | 同類的事不必再講一次 |
| 3 | 回顧：每週挑幾筆後果大的判斷問「後來怎樣」，看標準怎麼變 | 回饋吸收 3 → 4 | 用前兩步的資料；這一級沒有工具到達；就是北極星 | 判斷有記結果的比例上升 |

脈絡範圍與留存深度維持不動，它們是這條路的底。並行規模不往上推。

**時間上的考慮**（對照第六節）：第 1 步要趁早，驗收是現在的戰場，平台已經開始內建機器審查。
第 2 步落在「下一批才會長出成熟工具」的地方。第 3 步是最晚才會有人到的地方，可以走得最久。

每一步都留在「以人為單位」上，所以累積下來的驗收、標準、結果是別人拿不走的東西，也是這條路能一直走的原因。

**配套的原則**：

- 擋的條件用後果：對外、收不回來、跨範圍、碰到真實使用者或資料、會留下還在跑的東西。
- 能交給監督 agent 的驗收先交，人只驗 agent 碰不到的。
- 放行的單位是任務，不是類別。
- 品味類的提問不要做成選項，給「看這個、說哪裡不對」。
- 跨 repo 要的是指路，不是找路；引用跟著讀取走，不跟著某個工具走。
- 交接要寫「我沒驗到什麼」。
- 事故要有痕，否則上面每一條都驗不了。

**不做的**：執行台功能；用搜尋與推薦帶案情。

## 限制

- **意圖釐清 4 與回饋吸收 4 是空的，可以是機會，也可以是沒有人要。** 現有資料分不出來。第 3 步最沒有被證明。
- **刻度表的分數是一個人依 README 與搜尋結果打的**，沒有實際用過這些工具；刻度的切法也是我定的，換一種切法分數會變。
- **九條維度量的是協作的姿態。** 沙盒、核准、可觀測性這類管線工具多數欄位不適用；執行台彼此在「會話活不活得下來」上的差別也量不到。
- **九條維度是看完這些工具之後定的**，還沒被沒看過的工具檢驗。只有兩條對得上既有文獻的術語。
- **趨勢是歸納來的。** 十一個個案是我挑的，沒有完整的時間序列；歸納只能說到目前為止都這樣。
  「越靠近人的問題越沒人解」也可能不是還沒輪到，而是做不成產品。
- **回測樣本小**：70 筆、9 天、4 個 repo，歸類是一個人做的；會話中間的問答不在 spine 裡。
- **外面的證據多半來自寫程式**，研究與知識工作是類推的。
- **「以人為單位」這個結論對本 repo 有利**。平台如果把記憶做到使用者層，脈絡範圍與留存深度的優勢會更快被收掉。
- **幾個數字是二手或工具摘要**：METR 的時數、2610.34748 的相關係數、Chen 與 Stratton 在新聞裡的百分比。

### 這份文件怎麼改過來的

同一天改了五次，每次都是被資料或使用者更正：

1. 第一版把人的工作講成「下決定」。回測顯示等人的事 78% 是驗收。
2. 我用工具呼叫次數推論「跨 repo 幾乎沒在用」。使用者指出他常直接指路，會話紀錄證實是 114 次對 8 次。
3. 評估維度換過四種講法（時機 × 寬度、邊界 × 帶什麼、五個動作、三條合成軸），都太複雜或有工具放不進去。
   最後照使用者的要求，改成九條各有刻度的維度，並逐一替工具打分。
4. 我說過「跨 repo 帶標準沒有人做」。擴大搜尋後找到至少五個規則同步工具。
5. 我把「時機 × 寬度」掛在一篇綜述名下。回頭讀原文，論文只有同步與非同步這一條；「一件或多件」是我自己的意思。

共同的教訓：把容易量的東西當成實際行為，以及引用時沒有回頭核對原文。
