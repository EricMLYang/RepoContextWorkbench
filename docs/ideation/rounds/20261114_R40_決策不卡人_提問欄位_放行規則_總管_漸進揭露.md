## 2. 產品主張

**人只看真正要人判斷的事，而且每一件都在 30 秒內看得懂、答得完。**

三個機制，一個依賴一個：

1. **提問欄位**：agent 停下來等人時，必須把問題寫成結構（問題、選項、建議、類別、可逆與否、證據）。
2. **放行規則**：同一類問題你連續同意幾次後，工具問你「以後這類都照這樣？」；你點頭才升級，之後自動放行並留痕。
3. **總管**：不屬於任何 repo、站在 spine 上的 agent 會話，開場就拿到全局（等你幾件、自動放行了什麼、registry 變了什麼）。

另外兩件配套：

4. **漸進揭露**：agent 找別的 repo 的資訊時，一步只給一小塊，並指出下一步。
5. **畫面**：收件匣把「要你決定」獨立成最上面一區，其餘收起來；總管有一個固定入口。

## 3. 設計決定（與理由）

| 決定 | 理由 |
|---|---|
| 類別用固定清單，不讓模型猜相似度 | 人要看得懂為什麼兩件事被歸成一類；規則要能手改 |
| 升級一定要人點頭，推翻一次就降回每次都問 | 學習機制最怕悄悄變寬；`VISION` 的北極星是人的判斷變好，不是代工 |
| 不可逆、對外送出、刪除、push 永遠不能自動 | 寫死在引擎，不是設定 |
| 規則存成 spine 裡的純文字（`policy.yaml`） | 資料格式就是合約；人看得到、改得了、跟著 git |
| 統計不另存計數，從 spine 事件算 | 留痕只有一份；規則檔只存「人同意的等級」 |
| 總管第一版只能提建議，不能代答 | 代答的唯一途徑是放行規則（已經過人同意）；總管答錯會被下面的 agent 放大 |
| 提問欄位寫成交接事件裡多幾行「鍵：值」 | 跟現有的「完成：／剩下：／下次從這裡接：」同一種格式；只加不改 |
| `search_knowledge` 的 MCP 預設改成精簡，CLI 預設不變 | agent 會照預設用；CLI 是對拍合約。刻意差異要寫進 `RUST_PORTING.md` |
| 不寫任何東西進使用者的 repo | `VISION` 的最小打擾；安裝本來就是使用者層級一份 |

## 4. 分輪

每輪的「完成」定義：`bash scripts/check.sh` 全過；用 spine 副本跑真資料，輸出由 Fable 逐項讀過；合約變更寫進文件。
真 spine（`repo-spine`）在整個過程只讀。

### 第 1 輪：提問欄位與決策佇列（F-123）

- **引擎**：`handoff` 多一個選填的 `ask`（question、kind、options、recommend、reversible、evidence）。寫進交接事件、`parse_handoff` 讀得回來。
- **類別**（固定 enum）：`commit`、`content_review`、`config_change`、`choose`、`visual_check`、`manual_test`、`push`、`publish`、`delete`、`send_external`、`other`。
- **新模組 `decide`**：
  - `ctx decide list [--group G｜--all]`：列出要你決定的卡。每張：repo 一行介紹、問題、選項（編號）、建議、證據、放了多久。有結構化提問的排前面，其次是只靠文字判斷出「等你」的舊交接。
  - `ctx decide answer <repo> <選項編號｜文字>`：留一筆痕（答了什麼、是否照建議），並回傳送達方式（沿用 `relay::answer`，只印不開會話）。
- **接力**：有 `ask` 的交接直接算「等你」，不再只靠 regex。
- **MCP**：`handoff` 工具加 `ask` 參數；描述寫清楚什麼時候要填。
- **驗收**：舊交接照舊解析；spine 副本上 `decide list --all` 列出現有 9 件；寫一筆帶 `ask` 的交接後排在最前、選項可用編號回答；答完那張卡消失、留痕查得到。

### 第 2 輪：放行規則（F-124）

- **`policy.yaml`**（spine 根目錄）：`rules: [{repo, kind, level, paths?, since}]`，level＝`ask`｜`auto`。
- **新 MCP 工具 `request_decision`**：agent 做到一半需要人決定時先呼叫。回 `auto`（附答案與規則依據，agent 接著做）或 `wait`（agent 照舊交接並等）。
- **放行條件**（全部成立才自動）：有 `auto` 規則；類別可自動；`reversible` 為真；有 `recommend`；規則有 `paths` 時，repo 沒 commit 的檔全部落在裡面（引擎自己用 git 驗，不信 agent 的說法）。
- **升級建議**：同一個（repo、類別）最近連續 3 次都照建議回答 → `decide list` 與 `decide answer` 的輸出多一句「以後這類都照建議？`ctx decide trust <repo> <kind>`」。
- **`ctx decide trust｜untrust`**：人明確升降級。`decide answer` 的答案跟建議不同時，該規則自動降回 `ask`。
- **抽查**：每 10 次自動放行有 1 次照樣問人。
- **事後清單**：`ctx decide list --auto`（最近自動放行的，附 `ctx decide overturn <ref>`）。
- **驗收**：沒規則時永遠 `wait`；`delete`／`push`／`reversible=false` 即使手改 `policy.yaml` 成 `auto` 也回 `wait`；連續 3 次同意出現升級建議；`trust` 後第 4 次回 `auto` 並留痕；`overturn` 後降回 `ask`；`paths` 外有改動時回 `wait` 並說明原因。

### 第 3 輪：總管（F-125）

- **`ctx registry changes --since <時間>`**：這段時間登記、移除、改名片、改類別、改組的清單；加上現在路徑不存在的 repo。
- **`ctx steward`**：總管簡報，≤ 2 KB：要你決定幾件（前 5 件各一行）、自動放行幾件待看、有升級建議的類型、registry 變更、各組一行（等你／在跑／沒動靜）、工具版本與健康指標的異常。
- **spine 開場**：在 spine 目錄開會話時，SessionStart 注入同一份簡報加總管的作業規則（只讀全部 repo；可以用 `ctx decide suggest <repo> <建議> --why …` 在卡上留「總管建議」；不能代答、不能改別的 repo）。
- **`ctx decide suggest`**：卡片上多一行總管建議；人回答時看得到。
- **`ctx session --steward`**：用 spine 當工作目錄開總管會話（App 入口第 5 輪接）。
- **驗收**：spine 副本上開場輸出 ≤ 2 KB 且內容對得上 `relay plan`、`decide list`；未登記目錄仍輸出 0；一般 repo 的開場大小不變。

### 第 4 輪：漸進揭露（F-126）

- **`search_knowledge` 精簡模式**（MCP 預設、CLI `--brief`）：≤ 1.5 KB。`answer_repo`（最相關的 repo、理由、一行介紹）、`refs` 最多 3 筆（各一行片段，保證含 `answer_repo` 的檔）、`decisions` 最多 2 筆、`next`（下一步能叫什麼）。`detail: "full"` 拿回現在的完整輸出。
- **排序修正**：路徑含 `archive`／`retired`／`deprecated` 的檔降權；「標題命中」要命中一半以上的查詢詞才標。
- **新 MCP 工具 `repo_entry`**（CLI `ctx repo entry <id>`）：入口卡 ≤ 1 KB。這個 repo 是什麼、路徑、從哪幾份文件讀起（README、AGENTS.md、docs 索引、exports）、最近 2 筆判斷、最後交接一行、現在有沒有人在改。之後 agent 自己用 `grep`／讀檔，不再經過 ctx。
- **判斷歸屬**：`decisions` 段標出「在哪個 repo 的會話裡記的」與內容提到的 repo 不一致的情況（今天查 `draftagent` 會混進講別的 repo 的判斷）。
- **skill 與開場約定**：改成「先 `search_knowledge`（精簡）→ `repo_entry` → 自己讀」，一句話講完。
- **驗收**：10 個已知答案的查詢，精簡模式的 `answer_repo` 命中數不低於完整模式的 `repos` 第一名；回傳位元組數量測；小型 A/B（同一題，agent 只能自己查 vs 可用 ctx，比工具呼叫數與答對）。

### 第 5 輪：畫面（F-127）

- 收件匣上方「要你決定」區：一張卡＝repo 一行、問題、選項按鈕（建議的那個是主要按鈕）、證據連結、總管建議、升級建議。鍵盤數字鍵選、Enter 送。
- 其餘 6 類卡收在「其他」，預設摺起來。
- 工具列三個按鈕（存成今日簡報、這組標為已讀、所有組標為已讀）收進一個「⋯」。
- 左側所有組的最上面固定一列「總管」，帶要你決定的件數；開會話對話框第一行寫範圍與能做什麼。
- 自動放行清單與推翻。
- **驗收**：vitest 與 axe 場景加入；`preview.html` 新場景用 headless 截圖看排版。真 App 的點擊流程要使用者測，寫進 `TESTING.md` §8h。

## 6. 風險

- **agent 把類別標錯來過關**：靠 `paths` 這種引擎自己驗的條件，加抽查。
- **提問寫得差**：卡片照樣難懂。MCP 描述要給好壞各一個例子；總管可以補建議。
- **冷啟動**：一開始什麼都要問。不自動從歷史種規則（那等於沒經過人同意）。
- **證據薄**：外部做法多是實務者與廠商的文章，沒有嚴謹量測。所以第 5 節的數字要真量。
- **接力第 2 輪的 8g-3 還沒人測過**：`decide answer` 沿用它的送達方式，那一步不通，這裡也不通。
