## 2. 對標掃描
- 查詢：見 `benchmarks.md`「用過的查詢」R01 共 7 條。
- 市場形狀（💭）：
  - **平行執行**已經很成熟（Orca、Conductor、Vibe Kanban、Sculptor、Nimbalyst），幾乎都是 worktree 加終端機加 diff 審查。
  - **repo 變成知識**分成三條路：預先整理（DeepWiki）、持續編譯（Karpathy LLM Wiki）、打包成技能（skills／plugin）。
  - **git 裡的任務記憶**以 Beads 為代表，影響了 Claude Code Tasks。
  - **記憶層**往「有時效的事實」走（Graphiti）。
  - **沒有任何一個同時管跨 repo 關係和判斷沿革**。0901 那輪的結論「把 N 個 repo 收斂給一個人下判斷，這個形狀市面上是空的」依然成立。
- 定位結論：不跟 Orca 拼終端機和 worktree，做它們都缺的**脈絡層加判斷留痕**（F-31、F-28）。

## 3. 功能構想（ID 對 backlog.md）
依「repo 抽象化成什麼」分類，共 39 項：
- **專家** F-01～F-05：名片、常駐專家、專家會議、可信度、反方專家
- **知識庫** F-06～F-11：LLM Wiki 編譯、有時效的判斷、矛盾偵測、術語表、知識週報、靜態頁
- **流程 SOP** F-12～F-15：Playbook、交接把關、規格驅動、從操作序列長出流程
- **技能包** F-16～F-18：組匯出 plugin、技能目錄、從判斷提煉技能
- **任務圖** F-19～F-21：相依關係、完成條件、未結事項自動清理
- **判斷品味** F-22～F-24：判例搜尋、判斷回顧、品味檔案
- **學習路徑** F-25～F-27：能力地圖、書摘轉練習、間隔複習
- **執行層** F-28～F-31：同題多 agent 比較、成本帳、會話重播、當其他工具的脈絡層
- **跨 repo** F-32～F-34：上游改動起 PR 草稿、相關 repo 建議（#11）、Incubator 一鍵轉 repo
- **觀測與入口** F-35～F-39
