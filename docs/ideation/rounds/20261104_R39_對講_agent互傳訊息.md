## 0. 這輪的現況輸入
- 目標（AGENTS.md）：更快拿到對的脈絡、判斷有留痕、人和 agent 走同一個介面。
- 現況盤點：跨 repo 的能力全是**單向的讀**——`search_knowledge`／`read_from`（讀檔、留引用）、`ask_repo`（另起一次性 `claude -p`，慢、花額度、沒有對方正在跑的那個 agent 的脈絡）。
  App 已經能同時跑好幾個 agent 會話、知道每場在做什麼（hook 寫的 session_status），但**agent 彼此看不到、也說不上話**：
  draftagent 的 agent 需要工作台加一個 MCP 參數時，得由人把需求複製到另一個終端，做完再把結果貼回來。
- 這就是「多 repo ＋ Agent ＋人協作」最大的缺口：協作的單位是 repo，但 repo 之間的 agent 沒有通道。

## 1. 突破點的判斷
- 不是再加一種「讀」，而是補上 **agent ↔ agent 的通道**，並且守住本工具的兩個原則：
  1. **留痕**：每則訊息是 spine 事件（git、可搜、收件匣看得到），不是藏在某個程序的記憶裡。
  2. **打斷要自己掙得**：正在做事的 agent 在下一個工具結束時收到（不打斷）；閒著的 agent 只有「它自己問的問題有回覆了」才由 App 代打；別人的新請求交給人在收件匣決定。
- 「存在感」的兩半：agent 看得到同組誰在跑、在做什麼（名冊 `working_on`、`messages.peers`）；人在會話列一眼看到誰在等誰回覆。

## 2. 對標掃描
- MCP Agent Mail（Dicklesworthstone）：agent 身分、收件匣／寄件匣、討論串、檔案預留（lease）、pre-commit 擋別人預留的檔。
  差異：它是另一個 server＋資料庫；我們把信放在 spine（同一份留痕）、靠 App 已有的 Claude Code hook 把信送進**正在跑的**會話，回覆自動回到發問者——不用 agent 記得去收信。
- 檔案預留（lease）先不做：名冊已經講「N 個檔還沒 commit（可能正在被改）」＋「agent 在做什麼」，先看真用時有沒有撞檔。

## 3. 功能構想
- **F-121 對講**（完成，見 backlog）：`send_message`／`messages`（MCP）、`ctx msg send|list`（CLI）、hook 送達（PostToolUse／UserPromptSubmit／SessionStart）、回覆送回原會話、收件匣兩個出口、會話列標籤、名冊 `working_on`。

## 4. 非功能
- 送達路徑每個工具呼叫都會跑：先**不鎖**讀一次信箱檔，沒有信直接回（信箱檔不存在＝連讀都不讀）；有信才拿 spine 鎖標成已送達。
- 資料格式合約不變：不加事件型別，用 `suggestion`＋`〔對講〕` 前綴；Python 對拍 153 項全過（MCP 新工具與說明的一句記為允許差異）。
- 實測：真 Claude Code 2.1.318 在 `-p` 模式收到 PostToolUse 的 additionalContext，逐字讀出編號與內容。第一次它把 `send_message` 講成內建的 `SendMessage`，訊息改寫成「repo-context 的 MCP 工具 send_message（或 `ctx msg send`）」。
