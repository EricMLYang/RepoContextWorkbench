# R43｜2026-11-20｜從四個工具延伸的外部盤點：跟 agent 協作、交辦的工具，共同點與趨勢

> 起因：使用者要求以 R42 的四個對象（Home Repo Pattern、Orca、Better Agent Terminal、Herdr）為起點延伸搜尋，
> 彙整這一類「提高跟 agent 協作、交辦效率」的工具，找出顯著的共同點與趨勢（功能、痛點、期望）。
> 這一輪只蒐集與歸納，不量基準、不改程式、不動 `backlog.md`／`benchmarks.md`；最後一節列出對本 repo 的意思，都是 💭。
> 查證標記：✅ 讀過原文｜🔗 只看到搜尋結果｜💭 推論。

## 結論（先講）

1. **這一類工具都在解同一件事：產出變便宜之後，人的注意力變成瓶頸。** 幾乎每一家的開場白都是這句
   （Cline：「瓶頸不是 AI，是你」✅）。功能再多，都落在三個問題上：誰在等我、它做對了沒、我離開之後它還在不在跑。
2. **功能已經高度收斂**。worktree 隔離、「誰在等我」側欄、會話常駐、diff 逐行留言送回、不綁 agent 品牌、手機遠端，
   第三方與官方 App 幾乎人人都有。清單型的整理已經收了約 370 個同類工具（✅ 數字是約略值），另有一個「已停更」分類。
3. **官方平台正在把執行台吃掉**。Claude Code Desktop、併進 ChatGPT 桌面版的 Codex、Cursor 3 的 Agents Window、
   GitHub Agent HQ 都有平行會話＋worktree＋審查＋雲端。第三方剩下的立足點是「跨廠牌、本機、開放格式」。
4. **狀態回報正在從各家自己猜，變成協定**。OSC 7501 從十月初提出到現在約六週，41 個程式裡 21 個、24 個終端機裡 7 個已支援（✅）。
5. **瓶頸移到驗證之後，出現反向的聲音**：平行跑多個 agent 不一定比較快，實務建議的上限是 3–5 個，
   或乾脆回到「先寫規格與驗收測試，再放一個 agent 全自動跑」（✅ F2R）。兩邊的共識是：能平行多少，取決於驗證能不能不經過人。
6. **脈絡的做法收斂到「純文字檔＋指標」，而且越短越好**。Home Repo Pattern、meta-repo、Agent Skills 標準都是檔案；
   實證研究卻發現 AGENTS.md 寫多了會降低成功率、成本多兩成以上（🔗）。
7. **沒有人做的仍然是那一塊**：判斷留在哪、跨 repo 的時間軸、跨廠牌的交接。所有工具管的是「現在誰在跑」，沒有管「為什麼這樣決定」。

## 3. 共同的痛點

| 痛點 | 誰這樣說 |
|---|---|
| **人的注意力與審查是瓶頸** | Cline：「瓶頸不是 AI，是你」（✅）；Osmani：瓶頸是品味與「該不該做」，審查是瓶頸（✅）；F2R：產出堆在瓶頸前面變庫存（✅）；微軟訪談 17 位開發者：難的是審 agent 寫的程式（✅）；Anthropic 報告：六成工作用到 AI，能完全交辦的只有 0–20%（🔗 二手） |
| **不知道誰在等、切換成本高** | Cline：開了 20 個終端機，卡住或做完都沒發現（✅）；F2R：四個 agent 換來「四十段各三分鐘」的空檔，做不了設計也審不了東西（✅） |
| **agent 只看得到一個 repo** | Home Repo：從某個 repo 啟動的 agent 只看得到那個 repo，skill 與設定每個 repo 各一份（✅）；Codex 只從專案根目錄往下讀，從上層資料夾啟動會漏掉專案規則（🔗） |
| **會話一結束，脈絡就沒了** | 壓縮之後「計畫還在，為什麼不見了」（🔗 arXiv 2609.05510）；普遍的解法是交接檔：做完什麼、下一步、卡點、測試、分支；逐字稿不適合當交接（🔗）；跨工具的交接還是靠手動貼（🔗） |
| **隔離不完整** | worktree 只隔離檔案；七條平行線十分鐘就停、平行測試共用一個資料庫互相卡住（🔗 Since）；Gas Town 一週後留下 141 個孤兒行程（🔗） |
| **權限疲勞** | Claude Code 的權限詢問有 93% 被按同意（🔗 引 Anthropic）；解法是 auto mode 與 sandbox，但「agent 提議的放行規則被接受後永遠靜默執行」本身是攻擊面（🔗） |
| **成本與額度** | Gas Town「一天花幾百美元的機器」（🔗）；Codex 與 Copilot 在 2026 年 4 月、6 月改成按用量計費（🔗）；Stack Overflow：38% 的組織設用量上限（✅） |
| **工具換太快** | Superset 改名 Paradev、Crystal 變 Nimbalyst、Vibe Kanban 與 CodexMonitor 停更、Gas Town 改成 Gas City、Codex App 併進 ChatGPT 桌面版（🔗） |

## 4. 共同的期望

1. **從「自己寫」變成「管一小隊」**。Osmani 的說法是「async-first 的管理者」，配套是任務簡報（成果、脈絡、限制、不做什麼、驗收條件、
   驗證計畫）、WIP 上限、15 分鐘沒進度就停下回報、放棄條件、做完檢討並更新 AGENTS.md（✅）。
2. **一個地方看全部**。Cursor 3 把本機、雲端、從手機／Slack／Linear 起的 agent 放進同一個側欄（🔗）；Agent HQ 叫 Mission Control。
3. **人離開座位也能推進**。手機、雲端、排程是同一個期望的三種做法。
4. **不被單一廠商綁住**。AGENTS.md、SKILL.md、MCP、OSC 7501 都是「先有開放格式，再各家支援」。
5. **信任要有憑據**。Stack Overflow：93% 的人要看到出處才信 AI 給的東西；最被信任的脈絡來源是「專案目標與需求」85%，
   高於「程式與文件」73%（✅）。工具面的對應是證據產物：截圖、錄影、測試結果、PR packet（ProofShot、Cursor 🔗）。
6. **重複的指導變成資產**。研究觀察 19 位開發者：他們把力氣集中在規劃，把監督工作再交給別的 agent，
   把反覆講的指導做成可重用的東西（✅ arXiv 2609.24234）。skill 的流行就是這件事。

## 5. 趨勢

**T1 官方平台往上吃執行台。** Claude Code Desktop 已有平行會話、worktree、diff 審查、PR 監看、雲端與 SSH、會話互傳訊息（✅）；
Codex App 2026-02 推出、07-09 併進 ChatGPT 桌面版（🔗）；Cursor 3（04-02）改成 agent 優先，05-13 加多 repo 的雲端環境（🔗）；
GitHub Agent HQ 讓 Claude、Codex、Copilot 在同一個介面跑（🔗）。執行台這層對第三方越來越難守，這跟 R41 的判斷一致。

**T2 狀態從猜測變成協定。** OSC 7501（規格 0.4，2026-10）讓程式自己說 idle／working／done／blocked／error。追蹤頁（✅）：

| | 已支援 | 進行中 | 沒動 |
|---|---|---|---|
| agent | Claude Code（2.1.295，10-08）、Codex CLI（0.163，10-15）、opencode 2、pi、Amp | Gemini CLI、Kimi Code、OpenClaw | Cursor CLI |
| 終端機 | iTerm2、cmux、Orca（1.4.232，10-20） | kitty、Zellij、Herdr、Contour | tmux（10-09 關掉請求不做）、Ghostty、WezTerm、Warp、Windows Terminal、VS Code |

它走的是 agent 自己的 PTY 輸出，所以 SSH 與容器裡也通，不需要另外的 socket（🔗）。R42 引用的 Orca 實測表與這張追蹤頁的版本對得上。

**T3 瓶頸移到驗證，力氣往兩頭移。** 前面是規劃：先寫規格與驗收測試（F2R ✅、研究 ✅）。後面是驗證鏈：
agent 做的時候就自己對著執行結果檢查（Augment 🔗）、交付時附證據、用另一個 agent 審（Osmani ✅）。
微軟的研究把監督分成四種：事前設限、一起規劃、即時監看、事後審查，並指出監督不只是事後的（✅）。

**T4 對「平行越多越好」的修正。** 實務建議的上限落在 3–5 個，WIP 要對齊審查量而不是算力（🔗）；
「我不再同時跑好幾個」的文章自成一類（F2R ✅、Since、Camunda 🔗）。F2R 的條件句最清楚：
「多 agent 站得住的那一天，是它不再需要我來驗證的那一天」；跑十個的人只是驗證鏈比較好（✅）。

**T5 脈絡用檔案管，而且要短。** Home Repo Pattern 一出來的評語是「無聊、理所當然、人人想要」（🔗）。
同時實證研究指出：AGENTS.md 這類脈絡檔會讓 agent 探索得更廣，成功率反而下降、成本多兩成以上，人寫的略好於生成的，
結論是只寫最少必要的（🔗 arXiv 2602.11988，ICLR 2026）。skill 也有對應的研究：同時裝的 skill 會互相衝突、
第三方 skill 有供應鏈風險（🔗 只看到標題）。

**T6 會話常駐變成基本配備，並往 Windows 擴。** wmux、Termexo、psmux、Pane 都以 Windows 原生為賣點，
理由是 WSL＋tmux 會弄壞剪貼簿與路徑（🔗）。VS Code 在 2026-08 發表 Agent Host 架構，主打會話持久與可攜（🔗 只看到標題）。

**T7 編排從大框架退回輕量原語。** Gas Town 的教訓整理下來：有用的是「狀態放在 agent 之外、會話可拋棄」，
失敗的是成本、孤兒行程、在大型程式庫上編排者自己迷路（🔗）。現在各家給的是小工具：開一個、送訊息、等回報。

**T8 多 repo 變成一級需求。** Home Repo Pattern（2026-11）、Cursor 3 預設多工作區且雲端環境支援多 repo（🔗）、
各種 meta-repo 寫法。共識是兩層：中央檔管跨 repo 的導航與規範，各 repo 的 AGENTS.md 管自己的建置與測試指令（🔗）。

**T9 計費改成計量，成本可見變成功能。** 額度表、多帳號切換、每任務花費上限都從外掛變成內建（🔗）。

## 6. 還沒有共識的

- **平行到底值不值得**：見 T4。廠商說是編排問題，實務者說是驗證問題。
- **編排要多重**：Gas Town 式的角色階層，還是 `run／send／wait` 三個指令。
- **狀態走哪條路**：hook 資訊多但要設定；OSC 7501 零設定但 tmux 明確不做、主流終端機多半還沒動。
- **脈絡該給多少**：做法在加（wiki、steering files、skills），研究說少給比較好。
- **本機還是雲端**：Osmani 的分法是「判斷類留本機高互動，範圍明確的丟背景」（✅），但各家雲端互不相通。

## 7. 對本 repo 的意思（💭，都沒進 backlog）

1. **定位再被驗證一次**。所有工具管的是「現在誰在跑、誰在等」；判斷留在哪、跨 repo 的時間軸、跨廠牌交接仍然沒人做。
   Stack Overflow 那一題（最被信任的脈絡是專案目標與需求，不是程式碼）跟 spine 存的東西是同一類。
2. **Home Repo 原文跟 R42 用的摘要有出入**：原文寫「約 20 個 repo 用一個檔沒問題，約 400 個才按領域拆檔，上千個改用 skill 市集」，
   不是「超過 20 個就拆」；另外寫「skill 最好跟著專案放，使用者資料夾是權宜之計」。23 個 repo 用兩層不算錯，只是不是文章的建議。
   這一點來自抓頁工具的節錄，值得你自己看一眼原文再決定要不要改 R42 與 `benchmarks.md` 的那一列。
3. **F-130（OSC 7501）的外部證據變強**：Claude Code、Codex 都列為已支援，Orca 也已支援；這條路不再是賭注。
4. **開場注入與生成的 AGENTS.md 要守住「短」**：T5 的研究支持 11-18 把內建 skill 從 146 行縮到 30 行的方向。
5. **決策卡附證據，對上「信任要有憑據」**；收件匣如果能看到「等你審的有幾件」，就是 WIP 上限的資料來源。
6. **F-134（會話索引）要先確認逐字稿保留天數**：Claude Code 預設 30 天清掉，索引只掃得到還在磁碟上的。
7. **執行台功能繼續不追**：T1 之後連第三方都難守，R41 的結論不變。
