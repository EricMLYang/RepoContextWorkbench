## 1. 兩個產品一句話

| | Orca（stablyai/orca） | Better Agent Terminal（tony1223/better-agent-terminal，簡稱 BAT） |
|---|---|---|
| 是什麼 | 「AI Orchestrator」：多個 CLI agent 各開一個 git worktree 平行跑、在同一處追蹤 | Tauri 終端聚合器：多工作區終端＋內建 Claude Code／Codex 面板 |
| 技術 | Electron＋React；背景 daemon 擁有 PTY；CLI `orca`；手機 App；SSH／WSL／雲端 VM | **Tauri 2＋Rust host＋React**，只在必要處留 Node sidecar；Rust 拆 9 個 crate |
| 把 repo 當成 | 一個任務一個 worktree（執行容器） | 一個資料夾一個工作區（終端群組） |
| 規模 | 巨型（src/main 上百模組、數萬 PR） | 中型（單人主導、計畫文件很完整） |

兩者都**不管跨 repo 脈絡、不留判斷**——這是本 repo 的位置；但兩者在「agent 會話的生命週期與狀態」上做得比我們深很多，這是本輪主要的抄點。

## 2. Orca：設計哲學

1. **執行端擁有狀態，讀者只做呈現**（AGENTS.md「Agent Status」）：agent 狀態只有一個 store（hook server 的），側欄、`worktree ps`、手機、dashboard 全部訂閱它。新的生產者寫進同一個 store，不各自猜。
   → 對照：我們的 `.state/session_status/<sid>.json` 由 hook 寫、App 讀，方向一致。
2. **存活判定的詞彙是固定的**：`live`／`unverifiable`／`exited`，「失聯不等於死亡」，只有正向證據才能停、丟、重試。
3. **讀 agent 畫面的規則要對著錄下來的逐字稿寫**，不靠記憶中的畫面（`capture-agent-pty-transcript.mjs`）。
4. **混合式 skill**：裝進 agent 的 SKILL.md 只是薄薄的 stub（何時用、怎麼找到 CLI），完整指南用 `orca skills get <topic>` 從**版本相符**的執行檔拿；App 偵測已裝的 skill 過時會提示更新。
5. **工具輸出給程式讀**：每個指令 `--json`、回傳收據（`operationId` 可重試、`prompt.outcome` 說提示有沒有送達）。
6. **不搶焦點**：測試與 agent 開的 App 一律背景啟動、不 `show()`／不 activate；UI 驗證用 CDP 截隱藏視窗——跟我們「GUI 自動化只鎖定受測 App」同一個病史。
7. **Reuse before reimplementing、檔名要說清楚內容**（禁 `utils`／`helpers`）、註解一行講 why。

| Worktree checkpoint | 每個 worktree 一個自由文字 comment＋卡片狀態，agent 在里程碑用 CLI 更新；「寫之前先讀，別蓋掉人寫的目標」 | 等同我們的 `report_status`＋交接；「先讀再寫」可放進 skill 提醒 |
| Annotate AI Diff | 在 diff 任一行留言，**整批**送回 agent（一次思考、一次修改，命中率高）；未解決的留言下次再送 | 我們有「變更→差異」，但看完只能自己打字給 agent（→ F-75，P2） |
| 首次工作自動改名 | 依第一句提示幫分支／資料夾／會話取名 | 併進 F-71（用 Claude Code 自己的 `ai-title`） |
| Hibernation | 做完、閒置 30 分、可 resume 的 agent 才凍結；回來時用 resume 旗標接上 | 單人用量不需要；但「可 resume」這個前提就是 F-72 |
| Automations | 排程跑 prompt，`--precheck` 先跑便宜的 shell 探針，失敗就記一筆 skipped | 我們的 timer 可抄 precheck（記入構想，不做） |
| Orchestration | Run／Task／Dispatch 三層；`worker_done` 一定要帶 `--outcome succeeded|failed`，「別只把失敗寫在散文裡」 | 對照我們的 handoff：**結果要結構化**——close_todo 帶證據（F-20）方向一致 |

## 4. BAT：設計哲學

1. **IPC 是相容性合約**：既有 `host.*`、事件名與形狀只能加不能改；新 runtime 要轉成舊事件形狀；fallback 發生在合約之下，不逼前端改。→ 跟我們「資料格式就是合約」同一句話。
2. **一個會話的 runtime 歸屬要明確**（Rust 或 Node 二選一，不混）。
3. **Rust crate 拆分規則**：crate 不依賴 Tauri、不碰視窗與會話狀態；host 擁有 store／watcher，把路徑與 callback 交給 crate。我們的 `ctx-core`（引擎）／`ctx-cli`／殼的分法一致，BAT 更細（pty、git、filesystem、app-storage、remote-protocol 各一個 crate）。
4. **計畫文件是給下一個 agent 的交接規格**（`plans/*.md`：一段摘要、已驗證的積木表、還沒做的、為什麼這樣設計）——跟我們 `ctx todo brief` 的任務包同一個想法，但 BAT 直接寫成 repo 內文件。
5. **對訂閱計費的判斷寫進設計**：`plans/claude-cli-transcript-agent-plan.md` 引 Anthropic 2026-06-15 生效的政策——**互動式** Claude Code 算訂閱額度；**程式化**（`claude -p`、Agent SDK）走另計的額度。所以 BAT 選擇「PTY 跑互動 CLI＋讀逐字稿 JSONL＋hook 只當控制訊號」，不用 `-p`。
   → **對本 repo 是重要提醒**：App 助手（`assist_plan`）、碰撞判定、`ask_repo`、backfill 抽取都用 `claude -p`。要不要在畫面上註明「會用到程式化額度」，是使用者的決定（→ 開待辦，不改行為）。
