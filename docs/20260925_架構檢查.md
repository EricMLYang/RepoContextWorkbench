# 2026-09-25 架構檢查：以可擴充性、持續加功能的角度

> 起因：牌組維護（加減組員／改名／刪組）一個功能改了 registry → CLI → webui → MCP 四處，
> 「記一筆 decision」寫了三份、措辭還不一樣。使用者請求重新檢查架構，看要不要重構。

## 1. 結論

**要，但只動寫入路徑與三個大檔；不重寫。** 事件脊椎、spine 格式、各 P 模組、agentapi 工作層、
測試（不變式 + e2e）都站得住。問題集中在兩處：registry 寫入有實錘 bug、每個入口各寫一份。

## 3. 重構中順手抓到的語意問題（都先補測試再修）

- **CLI 改設定的留痕會進收件匣**：來源 `[manual]` 不在「自己出手」清單。→ 操作表依入口定來源：
  CLI `[cli]`、工作台 `[monitor]`（都不進收件匣）、MCP `[agent]`（agent 改了你的 registry，要看得到）。
- **改設定被工作摘要當成「上次進度」**：建組、改目標都是 decision。→ 操作表留痕的 body 帶
  `〔registry〕` 前綴（`spine.ADMIN_TAG`），`summary` 的上次進度略過它；會話結果、交接照算。
- **工作台編輯牌組、MCP group_update 可能只改一半**：→ `registry.update_group` 一個 transaction 做完增減／整份換／改名。
- **工作台 tag 未知 repo 回 500**：→ 走操作表後是 400 帶訊息（使用者錯誤不是伺服器錯誤）。
- **CLI 的 registry／group 錯誤是 traceback**：→ 走 `_fail`，`--json` 時回 `{ok:false,...}`、exit 2。

## 4. 加功能的路徑（之後）

1. 管理類寫入（registry／組／關係／export）：`ops.py` 加一個 `@op` → MCP 管理層自動多一個工具。
2. CLI：`cli/admin.py` 的 `register()` 加一行 `action(...)`；其他領域放對應模組的 `register()`。
3. 工作台：`webui/actions.py` 加 `_a_<名稱>`（管理類用 `_via_op` 轉接），放進 `ACTIONS`。
4. agent 工作層：照舊進 `agentapi.py`（它本來就是一份邏輯、三個入口）。
5. 前端改完 `npx prettier --write repo_context/static repo_context/workbench.html`。

## 5. 驗證

- L1＋L2：223 passed（原 217 + lost-update／原子寫入／transaction 回滾／操作表同源／收件匣分流／進度規則）。
- pyright 掃新套件：拆檔造成的未定義名稱 0（抓到並修掉：`ws.py` 漏 `secrets`、函式內 `from . import`、
  parser 區塊裡的 `scoped` helper 跟錯模組、`_op(args, name, ...)` 參數撞名）。
- 真瀏覽器：工作台載入、編輯牌組（加成員＋改名）走新分派路徑，卡片留在原位。
- CLI 冒煙：`registry add/set/tier/tag`、`group add/rename/add-member`、`--json` 錯誤 exit 2。

## 6. 沒做的

- 工作台其餘 15 個 action（碰撞、loop、會話…）沒進操作表：它們是工作層動作、各有自己的回傳形狀，
  硬收進表沒有好處。之後若 MCP 也要同樣動作再收。
- `register_repos`（首次建組）仍直接呼叫 registry：它要「部分成功回報已登記的」，跟操作表的全有全無語意不同。
- JS 沒拆 ES modules（格式化已解決可讀性；拆檔等檔案再長一倍再說）。
- 其他 JSON 狀態檔（會話標記、快取、水位線）沒改原子寫入：各自單一寫者，沒有 registry 那種多入口併發。
