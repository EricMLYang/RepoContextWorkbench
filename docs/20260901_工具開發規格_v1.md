## 0. 五條骨架鐵律（每個設計決策都要過的濾網）

1. **通用引擎／私有分離**：引擎是足以開源的通用專案；repo 清單、路徑、偏好、儀式組裝全在私有層設定檔。引擎裡不出現「Eric」「PM_Head」任何字樣。
2. **資產是兩份純文字，程式碼是耗材**：registry（空間軸、就地更新）＋脊椎（時間軸、append-only）。引擎與薄殼 build-to-delete，模型與 harness 變強就扔；資料層永遠可被下一代工具直接讀。
3. **監控預設面過四條判準**：餘光可見、無事不報、有行動出口、打斷要掙得。全量狀態只存在於深看模式。
4. **本地優先、pull 式**：無伺服器、無 webhook、無雲端帳號；外部資訊在儀式時刻或手動觸發時用 API 拉。非即時是特性不是缺陷（打斷要掙得、進未讀等儀式時刻）。
5. **教練規格從第一筆日誌開始**：每個原語出手自動寫脊椎（呈現了什麼＋選了什麼＋依據）。這是 M1 的第一個實作項，不是之後補的。
6. **Agent 無關性**：引擎不綁任何單一 coding agent（harness 信念原句：「AI 大廠怎麼改版都能順著吃到，不被單一 IDE/CLI 綁住」）。agent 既是可插拔的**執行器**（P15/P16 provider），也是引擎的**使用者**（MCP）——兩個方向都走標準介面。

### 2.5 Agent 整合規格（雙向）

**方向一：引擎驅動 agent（P15，headless 執行器）**
- `AgentProvider` 介面：`run(prompt, context_files, cwd, options) → result`。v1 實作＝呼叫各家 CLI 的非互動模式（`claude -p`、`codex exec` 等），**不用 SDK、不自管 API key——認證沿用各 CLI 自己的登入，引擎零金鑰**。
- v1 支援清單：**Claude Code（必備、預設）**；第二家接 Codex 或 Gemini CLI 擇一先通，**目的是驗證 provider 介面真的中立**；其餘照介面擴充。
- per-任務指定：config 可為 P5（理解——便宜模型即可）與 P7（撞——要強模型）分別指定 provider／model。
- 標準化路徑：ACP（Agent Client Protocol）為候選——openab 已實證「改 config 就能換 agent」的可插拔性；**v1 不上 ACP**（headless CLI 呼叫最便宜），介面設計預留。

**方向二：人 ↔ agent 協作視窗（P16，帶料開視窗）**
- 流程：選 repo／組（或碰撞台當下的臨時組合）→ 引擎備料進工作目錄（P6 打包產物、組 digest、相關 spine 事件）→ 開原生終端視窗並啟動指定 agent CLI。直接命中 `工具想法.md` 痛點 2 原句：「挑出幾個 repo 不同文件，一次丟給某個 Coding Agent 彙整」。
- 形態：**開原生終端視窗，不內嵌 terminal**——BAT 花全職力氣才把內嵌做穩，殼是耗材，不做重投資。tray 選單、監控台的行動出口都可帶「在此開 agent」。
- session 預設 cwd＝spine repo 的 `groups/<g>/`（起始 skills 就位），也可指定任一 repo。

**方向三：agent 驅動引擎（既有設計，重申）**
- 引擎的 MCP server 把原語全數暴露——在任何 agent 視窗裡都能叫引擎做事（查 registry、寫脊椎、打包、路由）。**P16 開的視窗天生掛好這個 MCP**，所以協作中的 agent 隨時可以查牌、留痕、路由結果。

三個方向合起來＝Orca 那堂課的完整落地：**人的介面、agent 的介面、agent 的執行器，都是同一組原語。**

## 3. 資料規格

### 3.1 registry.yaml（空間軸，就地更新）——v1 草案

```yaml
repos:
  - id: some-repo
    path: ~/Repo/...            # 私有層路徑
    type: mine | external        # external＝別人的專案，參考用（需求 3 的對象）
    tags: [knowledge, dev]
    tier: active | paused | dormant | archived   # 沿用 PM_Head tier 制
    origin: collision:2026-09-15-a   # 血統：哪次碰撞生的它（工具生的必填）
    upstream: github.com/x/y     # external 才有；P4 查這裡
    relations:
      - {to: other-repo, kind: derived-from | feeds | sibling-topic | upstream-of}
groups:
  - name: agent-tooling
    members: [repo-a, repo-b]
    landing: default | own-repo   # 裁定 6：預設單一 spine repo，可選獨立
```

- relation 詞彙表是**起手式**（derived-from＝血統／feeds＝素材流向／sibling-topic＝主題相關／upstream-of＝上下游），用四週後再修——不預先設計完整本體論。
- 與 PM_Head `registry.yaml` 的關係（收斂檔開放問題 #3 的落地）：**個人層另立超集**，PM_Head 版日後可成為其子集；v1 不動 PM_Head。
- `type: external` 的監控語意不同：沒有 dirty/ahead-behind，只有上游更新（P4）。

### 3.2 脊椎（時間軸，append-only）——v1 草案

檔案切分（開放問題 #4 的落地）：**每日一檔**，每事件一個區塊。

```
spine/events/2026-09-01.md
---
## 07:42 presented [morning-brief] group:agent-tooling
呈現了：上游 3 筆更新、repo-x dirty 5 天、open loops 2 條
## 07:45 chosen [morning-brief]
選了：先處理 open-loop #12；忽略 repo-x（理由：本週不動它）
## 21:10 collision [hotkey] group:臨時(repo-a,card_notes)
輸入：<想法>；判定：真增量；落點：repo-a/01_inbox/
## 21:12 open-loop opened #13 → 「驗證 X 是否…」
---
```

- 事件型別 v1 起手六種：`presented`／`chosen`／`decision`（含當時考慮過的替代案，Obie `/decide` 式）／`suggestion`（建議與採納）／`collision`／`open-loop`（opened/closed——**狀態變化用新事件記，不改舊事件**，append-only 不破例；「目前未結清單」是 P11 算出來的視圖）。
- 這六種 ＝ 收斂檔五類 ＋ Szapar 的 open loops。

### 3.3 spine repo 結構（預設單一，裁定 6）

```
spine-repo/                  # 私有 repo
├─ registry.yaml             # 空間軸資產（兩份資產同 repo、不同檔、不同更新紀律）
├─ config.yaml               # 路徑、偏好、儀式組裝、provider 設定（公私切分線：全在這）
├─ spine/events/YYYY-MM-DD.md
└─ groups/<g>/               # 各組彙整落點
   ├─ digests/               # P5 產出
   ├─ materials/             # P6 打包產出、撞的素材
   └─ .claude/skills/        # 起始 skills（scaffold 時配置；清單見 §6 複用盤點）
```

- 公私切分（開放問題 #5 的落地）：**引擎 repo（公開）不含任何路徑與資料；spine repo＋config（私有）不含任何程式**。引擎啟動時讀 config 找到一切。
- 組選 `landing: own-repo` 時：P9 流程建獨立 repo＋出生登記，spine 的事件流仍寫回單一 spine repo（**脊椎永遠只有一份**，分出去的是彙整物，不是留痕）。

## 4. 監控規格（四條判準的落實）

| 層 | 內容 | 判準對應 |
|---|---|---|
| tray badge | 未讀事件數；正常時無 badge | 餘光可見／無事不報 |
| 通知（即時） | 只有三類准打斷：不可逆操作待確認、賠不起的異常、系統自認沒把握 | 打斷要掙得 |
| 通知（未讀累積） | 其餘事件（上游新版、dirty 過久、open loop 到期、碰撞結果待落）進未讀，儀式時刻集中呈現 | 打斷要掙得 |
| 每則通知 | 必附行動出口：〔開碰撞〕〔進 inbox〕〔開深看〕〔忽略並記錄〕 | 有行動出口 |
| 監控台預設面 | 只列異常與變化（含出口），空狀態＝「一切正常」一行字 | 無事不報 |
| 監控台深看模式 | 全量表格（欄位：repo/tier/分支/dirty/ahead-behind/上游更新/最後活動），主動點開才出現 | 裁定 1 |

**驗收方式**：拿 `workspace-stats`／`repo-healthcheck` 的死因當反向測試——「連續兩週，我沒有一次需要『記得去看』它，但該知道的都知道了」。

## 7. 技術選型（建議，M1 開工前定案即可）

- **引擎**：Python 或 TypeScript 擇一（Python 與既有 `tools/` 一致、TS 與 MCP 生態近；傾向 **Python**，理由：現有腳本資產與個人熟練度）。CLI 先行，MCP server 包同一組原語。
- **薄殼**：M2 最小版只需 tray＋hotkey＋通知——先用最便宜的跨平台方案（如 Tauri 極簡殼，或平台原生小工具）；**殼是耗材，選型錯了就扔，不值得前期糾結**。
- **平台**：Windows＋macOS 雙平台（實際工作環境）；引擎層純文字＋CLI 天然跨平台，坑集中在殼與排程（OS 排程器差異），M2 處理。
- **Agent 整合**：v1＝headless CLI 呼叫（`claude -p`、`codex exec`），認證沿用各 CLI，引擎零金鑰；不內嵌 terminal；ACP 為後續候選標準。
- **授權**：引擎 MIT／Apache-2.0（待選）；**不引入 AGPL 程式碼**（github-release-monitor 只能服務級對接）。
