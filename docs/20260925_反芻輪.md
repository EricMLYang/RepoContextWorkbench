## 1. 為什麼是這個功能

`docs/工具想法.md` 列了四個痛點，前幾輪把「多 repo 關係／統整」「挑 repo 餵 agent」「agent 接得上脈絡」
都做了；剩下兩個還只有半套：

- **知識吸收後怎麼讓其他 repo 得到好處**——`search_knowledge` 只會「拉」：agent 得先想到去搜。
  card_notes 每週新進幾十篇文章與卡片，跟另一組手上的事強相關時，沒人會想到去搜。
- **持續反芻所有決策與知識活動**——各組留下的判斷只在自己組內被讀到，不會和別組交匯。

兩個缺口是同一件事：**缺少「推」**——在會話之間，替每組先把相關的新東西找好，開場就擺在面前。

外部調研（2026-09）：
- Letta 的 **sleep-time compute**、Claude 的 **Dreaming**：在會話之間（不佔使用者的等待時間）
  讀過去的紀錄、先整理好，下次會話更便宜更準。Dreaming 是 copy-on-write——產出候選層，不動原資料。
- 第二大腦工具（Recall、second-brain-agent 類）這一年的主軸是 **resurfacing**：
  新存的東西自動找相關舊筆記、依手上專案主動浮現，而不是等人搜。
- 反面教材：多數做法靠 embedding＋LLM，推薦說不出為什麼、還要花錢；這個 repo 的紀律是
  「每一格都帶依據」「沒依據就說沒有」。

## 2. 落地

`repo_context/ruminate.py`：

| 步驟 | 做法 |
|---|---|
| 手上工作 | 每組＝目標＋未結＋最近 5 筆判斷／交接（全是寫下來的字；沒寫就不推，不從 commit 猜） |
| 候選 | 上次反芻後**別組** repo 新增／改過的 md＋別組新留下的判斷／交接；略過點開頭目錄、同內容去重 |
| 比對 | BM25（沿用 knowledge.py 的索引與快取）；共同**少見詞**（出現在 ≤10% 文件、不含虛字）≥3 才收；每組最多 3 筆 |
| 結果 | `.state/ruminate.json` 候選層，保留 30 天；**不進收件匣**（跟引用紀錄同理：不是要人處理的事） |
| 出口 | SessionStart 開場注入、`context_for.fresh`（MCP 同一份）、`ctx fresh` |
| 何時跑 | 排程 `task: ruminate`；或開場發現超過 20 小時沒跑 → 背景 detached 補跑（這次開場用上一輪結果，不拖慢開 agent） |
| 量尺 | 推薦出現後，組內有人 `read_from` 讀了它（cites.jsonl）＝用上了；`ctx fresh --stats` 命中率；`--dismiss` 略過 |

設定（config.yaml `ruminate:`）：`window_days`（第一次回看幾天，14）、`min_shared`（3）、`max_per_group`（3）。
