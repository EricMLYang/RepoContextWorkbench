> 各輪檢討與 R28 總回顧收斂而成；原始檔已從 repo 移除（要查當時的推導過程看 git 歷史）。
> 怎麼寫程式看 `DEVELOPMENT.md`；構想池與排序看 `ideation/`。

## 1. 一開始的目的

**出發點**：作者持續把知識、專案、開發都「repo 化」——有鍛鍊知識的 repo、累積判斷與品味的 repo、實際開發產出的 repo。
repo 化是信念，不是手段；這個工具要補的是 repo 化的代價：**repo 之間有牆**。

最早寫下的四個痛點：

1. **多 repo 的階層與統整**：專案底下一堆附屬 repo、追蹤中的外部專案、等著 repo 化的主題——同步、看關係、掌握狀況、git 操作都很累。
2. **跨 repo 彙整脈絡**：有新想法時，想快速挑幾個 repo 的幾份文件，一次丟給 coding agent 彙整。
3. **知識吸收後讓別的 repo 受益**：讀過的文章、書、卡片，很多跟其他 repo 強相關，希望能被比對出來、主動送到需要的地方。
4. **全面反芻**：所有專案與知識活動的決策、判斷，能持續交匯、追蹤、影響後續。

從這四點讀出來的事：

- **動詞全是「收斂」**（統整、彙整、比對、反芻），沒有一個是「幫我做更多」。要的不是 agent 代工，
  是事情流到面前時，已經是能直接下判斷的形狀。
- **這不是生產力問題，是成長系統問題。** 北極星不是省多少時間，而是：
  **回顧過去的自己時，能清楚看見判斷與品味變好了。**
- 痛點全在輸入側，但「回饋」才是最大的斷點——它被「彙整還沒做好」卡住，不是不重要。

## 2. 現在的定義

> 多 repo ＋ Agent ＋人協作的最佳工具：context 用 repo 管起來之後，讓人和 agent 都**拿得到、用得上、留得下痕跡**。

取捨準則（`AGENTS.md`，每個功能都要答得出對應哪一條）：

| 準則 | 意思 |
|---|---|
| **脈絡** | 更快拿到對的脈絡（人開工、agent 開場、跨 repo 參考） |
| **留痕** | 判斷有留痕：看到什麼、選了什麼、依據是什麼，日後能回看 |
| **同介面** | 人和 agent 走同一個介面：CLI、MCP、桌面 App 背後是同一個引擎、同一份 spine |

早期的說法是「**先當秘書、養出教練**」：秘書（70%）把訊號收斂成能下判斷的形狀；教練（30%）靠留痕給回饋。
教練的行為可以晚到，但**留痕的資料從第一天就不能缺**。

## 3. 核心概念（之後的設計都要守住）

- **操作單位是一手牌＝repo 組合**。起手式不是「打開一個 repo」，而是「這件事關係到哪幾個 repo」。一張牌＝一個 repo，牌要能便宜地生出來。
- **動詞鏈：挑 → 撞 → 落 → 生**。挑出 repo 組合 → 想法跟組合內容對撞（已知／衝突／真增量）→ 結果落到該去的地方 →
  主題夠格就升格成新 repo（**出生即登記**，記下血統；生得便宜，就要死得體面）。
- **資產與耗材分開**。資產是兩份純文字資料：**registry**（空間軸：有哪些牌、狀態、關係）＋**spine**（時間軸：
  看過、選過、決過、撞出過什麼）。其上的程式碼都是耗材（build-to-delete），模型變強就換。所以**資料格式就是合約**。
- **監控要過四條體驗判準**，否則形同虛設：
  **餘光可見**（出現在已經在的地方，不是要「前往」的頁面）、**無事不報**（只浮出異常與變化）、
  **有行動出口**（每個提醒自帶下一步）、**打斷要自己掙得**（不可逆或系統沒把握才打斷，其餘進收件匣）。
  全量狀態是可主動打開的「深看」，不是預設畫面。
- **通用引擎、私有資料**。repo 清單、路徑、偏好、儀式全走設定與 spine；引擎不含任何私人字樣，才能開源。
- **最小打擾：只讀使用者的 repo，不寫進去**（2026-10-13）。登記、分組、repo 介紹與協作角色、判斷、交接、索引
  全放 spine；repo 的內容、git 歷史、`.gitignore` 不因工作台多一行。能從 repo 現有內容推的就推（README、git log），
  推不出的由人或 agent 寫到 spine。
- **agent 是主要使用者之一**。工具依 agent 的工作切（開場 `context_for`、留痕 `log_decision`、收尾 `handoff`），
  輸出給程式讀（`--json`、可引用的 ref），跨範圍寫入要先問人。

## 4. 護欄（對著病史設的）

1. **沒有場合，不建功能**。每個功能要說得出它在哪個場合被用到（每天開工、寫作取材、週復盤、靈感碰撞、agent 開場／收尾）；
   監控類功能要過上面四條判準。答不出來就不做——防「造工具的次數遠多於用工具」。
2. **開源是畢業條件，不是起點**。架構第一天就分公私；公開整理要等真用穩定之後（原訂：儀式連續跑滿四週）。
3. **留痕從第一筆開始**。系統每次出手都記「呈現了什麼＋人選了什麼」。
4. **用真資料從使用者角度驗**。第一版常「功能對、體驗錯」，只有拿真資料副本讀輸出才抓得到。

品味怎麼量（北極星的操作化）：**靈感命中率**（過去的碰撞後來長成文章／repo／決策的比例）、**repo 存活率**、
**決策回看**（當時的選擇與依據 vs 後來的結果）。`ctx health` 的交接率、推薦命中率、判斷結果記錄率是第一版。

   | 交接率 | 76%（交接 28、沒交接 9） | 上升 |
   | 推薦命中率 | 0%（推 45、用上 0） | 推得少但準 |
   | 判斷結果記錄率 | 尚無資料 | 開始有結果 |
   | 未結：開 vs 關 | 開 46、關 6 | 關 ≈ 開 |

   同時要補：真實 Claude Code 會話走完「開場注入 → 工作 → 交接 → 結束」、App 畫面實測（N-21：R29 鍵盤流程已過，
   寫名片、⌘＋點挑檔、拖檔、差異切換這些點擊流程還沒）。重 build 後跑 `bash scripts/install-app.sh` 裝上；
   會話「等你」的 hook 只掛在 App 開的會話（`--settings`），不用重跑 `ctx setup`。
   真用時看：「等你」紅點是有用的餘光還是雜訊、挑檔用新會話還是貼到目前會話、⌘K 最常找什麼。
2. **合併回 main**：真用沒問題就合併，刪掉 Python 版與對拍，清掉程式裡的移植痕跡；換掉已封存的 `serde_yaml`。
3. **開源**：照 `DEVELOPMENT.md` §8 待辦（git 歷史、bundle id）與 §9（Releases、簽章、`ctx init` 一步上手、英文 README）。
4. **Windows（VDI）**：每個功能都要註明測過沒有；先發 CLI＋MCP。

**中期方向**（細節與排序在 `ideation/backlog.md`）

- **當其他 agent 工具的脈絡層**（F-31）：Orca、Conductor 等開的會話也自動掛上 ctx 的 MCP＋hooks——不跟執行台拼終端機，做它們缺的跨 repo 脈絡與判斷留痕。
- **跟平台記憶分工**（F-44）：單一 agent 的記憶交給平台；ctx 專注「本機、可讀、可改、在 git 裡」的跨 repo 判斷與人的收件匣。
- **常駐專家**（F-02）：每個知識 repo 有自己的記憶，記下被問過什麼、怎麼答。
- **待辦相依**（F-19）與**多 agent 比較同一題**（F-28）：等真用顯示需要再做。
- **前端效率**（N-09）：指令面板、慢動作可取消、無障礙稽核。
