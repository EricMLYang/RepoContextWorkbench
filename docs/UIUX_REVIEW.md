# UI/UX 檢討

> 檢討日期：2026-10-14。狀態：第一版設計提案；2026-10-15 已落地第一～三輪大部分（見第 9 節），GUI 尚未實機點過。依據：目前開啟的 macOS Repo Context「工作台」視窗、無障礙樹、實際頁面切換，以及 `desktop/src` 的對應元件。這是一份持續修訂的介面基準。

## 1. 結論與改版目標

目前的問題是**每個功能都有入口，卻沒有清楚的工作順序**。使用者要同時理解牌組、repo、檔案、會話、筆記、想法、事件與程序，再自己推斷下一個按鈕。把按鈕換成小圖示只能減少文字，無法解決這件事。

建議以「選工作範圍 → 接續 Agent → 檢查變更 → 留下結果」組織日常介面。搜尋與挑檔支援這條流程；管理、診斷與低頻操作退到各物件的次級選單。保留跨 repo 脈絡與判斷留痕，避免改版只剩下檔案瀏覽器和終端機。

第一輪優先做三件事：

1. 區分待辦、未讀與會話等待，讓數字和狀態值得相信。
2. 每個操作區只有一個主要動作，按鈕說清楚對象與結果。
3. 主內容取得足夠空間；右欄與終端不再無條件同時展開所有資訊。

以下頻率與配置是設計假設，並非使用紀錄的統計結論；以第 8 節任務測試決定是否採納。

## 2. 檢查範圍與證據界線

實際查看：檔案閱讀畫面（本文件）、工作區「檔案」、工作區「待處理」、左側牌組與會話、已展開的 Agent 終端、右側 repo 詳情。當時選中 MyProjects / RepoContextWorkbench，開著七份文件分頁及三個會話。

程式交叉核對：`Workspace.tsx`、`FileTabs.tsx`、`FileViewer.tsx`、`RepoPanel.tsx`、`RepoMenu.tsx`、`TerminalPanel.tsx`、`Composer.tsx`、`lib/view.ts`，並參考 `AGENTS.md`、`README.md`、`docs/VISION.md`。

未測：新使用者首裝、Windows、窄視窗實際操作、完整鍵盤與螢幕閱讀器流程、建立／終止會話及送出分析。沒有為了檢討執行 Agent 工作、改寫 spine 或結束既有程序。畫面中的資料新鮮度問題只確認了現象，尚未定位引擎根因；截圖也不作為色彩對比或精確尺寸量測。

## 3. 問題清單與優先序

P1＝先修，直接影響理解或操作方向；P2＝下一輪改善效率與可讀性。本次沒有觀察到足以判定 P0 的資料損失。

| ID／優先 | 觀察證據 | 使用者負擔 | 建議與驗收 |
|---|---|---|---|
| UX-01／P1 | 工作區可同時出現「開啟組會話」，右欄「開啟 Agent 會話」，摘要「接續上次工作」，左側已有等待中的會話 | 不清楚會接續還是新建、作用於組還是單一 repo | 有相符會話時提供明確「回到會話」；另列「新建 Agent 會話…」。新建視窗顯示範圍與成員，不能默默替使用者決定 |
| UX-02／P1 | 檔案工具列並排編輯、原始碼、加入挑選、差異、相對路徑、絕對路徑、重新讀取，共七個入口 | 閱讀模式、寫入動作與剪貼簿工具視覺同級；「相對路徑」甚至沒有動詞 | 改成模式選擇、編輯、加入脈絡、更多四組；複製與重新讀取進更多，異常時才就地顯示重讀 |
| UX-03／P1 | 右欄上方「未提交：乾淨」，下方「變更（2）」列出兩個檔案 | 使用者無法知道哪份資訊有效，反覆按更新 | 使用一致的 Git 快照或清楚標出不同採集時間；過期時顯示「待更新」，不能同時無註解地宣稱乾淨又列變更 |
| UX-04／P1 | MyProjects 標題寫「範圍內 81 件待處理」，內容分為待跟進 17、判斷回顧 5、其他未讀 59；其他未讀含別組 repo | 未讀被當成任務量，且「範圍內」與內容不符 | 分開顯示待跟進、待回顧、未讀；跨組消息單獨標示來源與範圍。先查資料契約，不直接把未讀刪掉或自動已讀 |
| UX-05／P1 | 終端列「看變更／記錄結果／結束程序…／收合」同級；Agent、Terminal 與左側 Shell 同時存在 | 使用者難分辨切換視圖、開新程序、記錄與停止的後果 | 停止移至會話更多；保留確認。Terminal 尚未存在時寫「開啟終端」，存在時才是切換。「記錄結果」改成帶會話對象的說明 |
| UX-06／P1 | 「記一筆」與「新增想法」並列；後者打開「碰撞台 · 分析想法」，程式送出 collide 並把結果送往收件匣 | 看起來都是存文字，實際一個是保存、一個會啟動分析 | 分別改為「寫組筆記」與「請 Agent 分析想法…」；送出前顯示範圍與結果位置 |
| UX-07／P2 | 工作區檔案頁和右欄同時有檔案樹、變更清單；右欄還放完整 Git 資訊與名片 | 同一資料重複佔空間，最常找的檔案藏在下方 | 右欄改為檔案／變更／資訊三個互斥頁籤；工作區跨 repo 檔案總覽保留，但進總覽時右欄預設收合，允許手動釘住 |
| UX-08／P2 | 七個文件分頁均附上長 repo 名稱；分頁列可見寬度不足以呈現全部 | 標籤重複，當前檔案難定位 | 預設顯示檔名，同名時才補最短辨識路徑／repo；提供開啟檔案清單，選中分頁捲入可視區 |
| UX-09／P2 | 左側每組都有大卡片、commit 數、編輯、展開、repo 與會話；下方另有「會話 3」，當下該區只列 Shell | 導覽兼做儀表板；總數與列表位置不一致 | 牌組改緊湊導覽列，保留等待數；commit 數移到總覽。下方若只列獨立 Shell，就命名「獨立終端」，總會話數放全域狀態 |
| UX-10／P2 | 頂部叫「找 repo」，README 顯示 ⌘K 實際能找 repo、檔案、會話與指令 | 入口名稱低估能力，功能發現依賴記憶 | 改「搜尋或執行指令 ⌘K」；結果標示類型與範圍，檔案搜尋說明限定目前工作範圍 |
| UX-11／P2 | 多處更新／重讀按鈕，另有全域登記檢查 16 項 | 使用者需猜更新什麼、16 項是否都必須現在處理 | 更新有明確對象；正常時退到更多，失敗時就地重試。登記檢查放管理入口，摘要只顯示可行動的異常 |

另見待處理內容有重複標題、已實作功能仍出現在待跟進，以及舊交接文字。這些是需核對的內容品質線索，不能僅憑同名就刪除事件，也不能把所有歷史任務判定完成。介面應顯示來源、更新時間與「可能已處理」證據，再由人決定。

## 4. 建議介面 V1

### 4.1 區域分工

- **左側：我在哪裡、哪些會話要回應。** 上方工作組，下方所屬會話；低頻管理進組的更多選單。等待狀態附文字，不能只靠紅點。
- **中央：我現在正在處理的內容。** 工作總覽或文件。工作總覽固定可回到；其子頁可先保留現有六頁，第一輪不急著重做所有資訊架構。
- **右側：目前 repo 的輔助內容。** 頁籤「檔案／變更／資訊」，一次只呈現一種任務；名片、完整 Git 資訊和管理入口放資訊頁。
- **下方：目前會話。** 顯示固定的會話範圍、狀態、Agent／終端切換。切工作組不應悄悄改變既有會話的執行目錄。
- **全域：搜尋與連線。** 正常連線縮為簡短狀態，失敗時才顯著展開原因和恢復操作。

閱讀文件時預設給文件較大高度，Agent 工作時允許放大終端；保留手動拖曳與既有使用者尺寸。不要每次切頁自動重置版面。

### 4.2 文件＋會話狀態示意

以下為提案線框，數字只示意當次觀察，不代表更新後即時狀態。

```text
┌ Repo Context                      搜尋或執行指令 ⌘K     已連線 ┐
│ 工作組             │ 工作總覽  UIUX_REVIEW.md  …  開啟檔案 ▾   │
│ Knowledge  等待 1   │ MyProjects › RepoContextWorkbench         │
│ MyProjects 等待 1   │ docs / UIUX_REVIEW.md                     │
│  RepoContext…      │ [閱讀 ▾] [編輯] [加入脈絡] [⋯]             │
│  Claude 等你回覆   │                                          │
│                    │ 文件內容                     │ 檔案 變更 資訊│
│                    │                              │ 目前頁內容    │
│                    ├──────────────────────────────┴──────────┤
│ 獨立終端           │ Claude · RepoContext… · 等你回覆           │
│  Shell             │ [Agent] [開啟終端] [查看變更] [⋯] [收合]   │
│ 管理工作組…        │ 會話內容與輸入                            │
└────────────────────┴─────────────────────────────────────────┘
```

工作總覽的重點順序：等待我回覆的會話 → 目前目標與最近交接 → 本組待跟進／回顧 → 可展開的未讀活動。每段顯示少量摘要及「查看全部」，保留完整內容入口。不要用巨大的未讀總數壓過真正需要決定的事。

### 4.3 操作層級與去向

| 現在 | V1 去向／命名 | 保留的語意 |
|---|---|---|
| 開啟組會話／開啟 Agent 會話 | 範圍標頭「新建 Agent 會話…」；repo 入口為次級 | 組與 repo 的作用範圍仍不同，不合併資料語意 |
| 已有會話 | 明確「回到會話」；多個時列選擇器 | 回到既有程序，不另開一個 |
| 原始碼／差異 | 單一閱讀模式選擇：閱讀、原始碼、與 HEAD 比較 | 顯示比較基準；新檔顯示「尚未追蹤」，不能假裝已有基準 |
| 加入挑選 | 加入脈絡；選中後「已加入脈絡 ✓」 | 只加入待交付清單，沒有自動傳送 |
| 相對路徑／絕對路徑 | 更多 → 複製相對路徑／複製絕對路徑 | 明確是複製；成功提示短暫且可辨識 |
| 重新讀取檔案 | 更多；磁碟變更衝突時就地呈現 | 有未儲存修改時保留衝突處理，不能為簡潔拿掉 |
| 記錄結果 | 會話更多 → 記錄本次工作結果…；收尾時可就地推薦 | 只是打開紀錄表單，不暗示會結束程序或 commit |
| 結束程序… | 會話更多 → 停止此會話程序… | 確認指出會話名稱；與收合、關窗清楚分開 |
| 記一筆 | 筆記頁「寫組筆記」 | 顯示將存入哪個組 |
| 新增想法 | 總覽次級入口「請 Agent 分析想法…」 | 顯示會啟動分析及結果回到待處理的位置 |
| 所有組標為已讀… | 全域未讀區的更多選單 | 明示「所有組」，保留既有確認；不代表完成待辦 |
| 全域登記檢查 | 管理入口下「登記檢查」 | 必須能找回；真正阻礙工作的錯誤仍就地顯示 |

不要把所有功能塞進同一個更多選單。檔案、repo、會話各有自己的更多；日常高頻任務保留直接入口。右鍵與快捷鍵是加速方式，不應是唯一入口。圖示按鈕必須具備可讀名稱與鍵盤焦點，不依賴 hover 才能發現。

## 5. 三條核心操作流程

### A. 接續工作

選工作組 → 看見等待中的會話與最近交接 → 點會話 → 輸入。

沒有會話時才突出「新建 Agent 會話…」。若選中工作範圍與下方會話不同，顯示「目前會話：Knowledge / …」，提供回到該範圍的入口，禁止只換標籤而不換實際執行對象。

### B. 閱讀檔案並交給 Agent

搜尋／檔案樹 → 閱讀 → 加入脈絡 → 挑選列顯示檔案數與目標會話 → 「貼到目前會話」或「交給新會話」。

「貼到目前會話」保留現有不自動按 Enter 的行為，介面說明「只貼上，尚未送出」。沒有可用會話時提供新建，不能留下無法理解的停用按鈕。跨 repo 的挑選項逐一標示 repo，切工作組也不能無聲清空。

### C. 驗收與留痕

會話等你回覆 → 查看 repo 未提交變更 → 選檔看差異 → 回到會話要求修正，或記錄本次工作結果。

「repo 的未提交變更」不等於「這個 Agent 改的檔案」；沒有歸因證據時不要如此標示。紀錄成功後應顯示落點與可查看入口；不能只用一則很快消失的成功訊息代替可回看的結果。

## 6. 視覺、窄視窗與狀態規則

- 每個任務區最多一個強調色主要動作；閱讀模式、更多、複製等採次級樣式。主要按鈕依明確狀態改變，但位置固定。
- 左欄由大卡片改緊湊列；工作組名稱、等待數優先，commit 統計退到總覽。選中組與選中會話應有不同層級的選取樣式。
- 長 repo 名稱允許截斷，完整內容可經 tooltip、鍵盤聚焦或資訊頁取得；影響操作的範圍和錯誤不可只截斷不提供查看。
- 窄視窗優先收右欄為可開啟面板，再收左欄；不把中央文件擠成狹長帶。以 1280×800、1440×900 和大視窗驗收，此輪尚未實測這些尺寸。
- 拖曳分隔線須有鍵盤替代方式；重要按鈕、選單、分頁應能 Tab 到達並呈現清楚焦點。終端快捷鍵避免攔截使用者要送給 shell 的按鍵。
- 非同步動作維持執行中鎖定、防重送、失敗就地重試、保留輸入；斷線時顯示最後成功資料及時間，不清空成像沒有內容。
- 狀態分開呈現「程序執行中／已停止」與「Agent 工作中／等你回覆／需要授權」。未知就說未知，不能由程序存在推論工作正在推進。
- 正常更新依既有事件機制；不要為了修新鮮度加上閒置輪詢。狀態一致性的業務規則仍由引擎提供。

## 7. 落地順序與程式對照

| 階段 | 工作 | 主要落點 | 完成條件 |
|---|---|---|---|
| 第一輪：讀得懂 | 七個檔案工具入口重組、想法與筆記改名、搜尋改名、停止移入會話選單 | `FileViewer.tsx`、`Workspace.tsx`、`Composer.tsx`、`Chrome.tsx`、`TerminalPanel.tsx` | 看標籤能描述動作結果；四組檔案工具可鍵盤操作；舊功能都有去向 |
| 第一輪：信得過 | 待處理／未讀範圍拆清楚、Git 狀態新鮮度一致 | `Workspace.tsx`、`inbox/InboxPane.tsx`、`RepoPanel.tsx`、`RepoChanges.tsx`，追查 store／引擎來源 | 同 repo 無互相矛盾的無註解狀態；跨組未讀不冒充本組待辦 |
| 第二輪：操作流暢 | 已有會話優先接續、repo 右欄三頁籤、檔案分頁縮短與清單入口 | `SessionRow.tsx`、`RepoPanel.tsx`、`FileTabs.tsx`、`PickTray.tsx` | 三條核心流程不用猜作用範圍；多會話、多 repo 均成立 |
| 第三輪：版面精修 | 左欄密度、窄視窗、焦點與拖曳替代、更多內容漸進展開 | `Sidebar.tsx`、`deck/Deck.tsx`、`Resizer.tsx`、`styles.css` | 小視窗無遮住關鍵操作；鍵盤可走完流程 |

先保留原本資料合約與能力，避免把 UI 改版擴大成引擎重寫。需要引擎調整的部分另列清楚：卡片範圍／計數、會話可接續狀態、Git 快照。React 不自行拼湊新的業務判定。此文件列的是建議落點，不表示已確認根因或完成修改。

## 8. 驗收方式

以下是待驗證的目標，不是本次測試結果。使用同一份測試資料、相同視窗大小比較改版前後；找 3–5 位未參與設計的人試做，另由日常使用者確認快捷操作沒有退步。記錄完成時間、首次點擊、誤開會話與求助次數，不只問「看起來清不清爽」。

| 任務 | 目標 |
|---|---|
| 說出目前組、repo、會話與下一步 | 10 秒內能指出；無需讀說明文件 |
| 回到已存在、正在等待的 Agent | 選定工作範圍後 2 次點擊內完成；不誤開新會話 |
| 看一份檔案並加入待交付脈絡 | 找到檔案後 2 次點擊內加入；知道尚未傳送 |
| 把所選檔案貼到目前會話 | 能辨認目標與範圍；不自動送出，不丟失原輸入 |
| 查看某 repo 未提交變更與單檔差異 | 會話畫面起 2 次點擊內到差異；知道比較基準 |
| 分辨寫筆記與請 Agent 分析 | 點之前能說明哪個只是保存、哪個會啟動工作 |
| 收合終端與停止程序 | 能說明差異；收合後程序仍可回到，停止維持確認 |
| 解讀待處理與未讀數字 | 不把未讀當未完成工作；能辨認跨組內容 |

回歸情境：無 repo、無會話、多會話、同名檔案、長路徑、未儲存編輯、Agent 同時改檔、未追蹤檔、讀取失敗、資料過期、斷線及重新連線。狀態與範圍修正需要行為測試；單純文案與樣式不另寫鏡像測試。實作後依專案規則執行必要檢查，並在 macOS 真實視窗重走上述任務；Windows 仍須獨立標示實測結果。

本版最先應驗證的設計假設：使用者進入 App 時主要想接續工作、檢查成果，而不是建立更多工作。若觀察顯示新建才是高頻任務，再調整主按鈕優先序；不要靠功能數量決定介面權重。
