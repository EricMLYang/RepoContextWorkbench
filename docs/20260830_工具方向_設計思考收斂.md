## 一、觀察（同理階段：從 Eric 寫的東西讀出的四件事）

**觀察 1：動詞全是「收斂」，沒有一個是「產出」。**
`工具想法.md` 的動詞攤開：統整、彙整、掌握、比對、反芻、交匯、追蹤、影響後續。沒有任何「幫我做更多、做更快、自動完成」。要的不是 agent 代工，是「事情流到面前時，已經是可以直接下判斷的形狀」——與素材檔 L2 判準一字不差。

**觀察 2：這是第三次畫同一張圖。**
`PM_Head_work` 的 `0_portfolio/`（手工版，停擺於 2026-05-22）→ `team-agent-hub`（部門版，規劃中）→ 本個人工具（第三次）。同一個形狀：分散活動 → 收斂 → 支撐判斷。強訊號：使用者一直回到同一個未被滿足的需求。**警訊同樣重要**：第一次的手工版死因不只是缺觸發器——週會報告從不缺席（有觀眾在等），`0_portfolio` 沒有任何人在等它。彙整的價值在被消費的那一刻，不在彙整本身。

**觀察 3：四個痛點全在輸入側，「驗證」缺席。**
痛點依序是收進來／組起來／連起來／消化掉，全是吃進去的方向；清單裡沒有「我想知道我的判斷對不對」。但素材檔量出的最大斷點恰恰是回饋線。此缺口本身是資訊。（→ 第 3 輪 Eric 裁定：回饋非常重要，是被「彙整監控還沒做好」卡住，不是不要。）

**觀察 4：「repo 化」是信念，不是手段。**
「我**會持續**將知識、專案、開發都 repo 化」是前提句。四個痛點是這個選擇的代價（repo 之間有牆）。工具的真正任務是補上 repo 化的代價，讓這個信念可持續。

## 二、為什麼梯子（逐層下探，每層皆有素材出處）

1. 為什麼多 repo 資訊不通會痛？→ 工作本質是**跨界收斂後下判斷**（PM Head 本業；寫作管線亦然）。
2. 為什麼跨界重組特別痛？→ 每次切換要人肉重建脈絡，而「記得脈絡」是 agent 唯一能無損接手的事（素材 3.7-B）。
3. 為什麼要知識外溢、全面反芻？→ 相信**知識要反覆對撞才會變成判斷**；`collide-capture` 是這個信念在卡片尺度的成功實作，現在要放大到 repo 尺度。
4. 為什麼要判斷與品味變好？→ 最終句：**成為某種人**。repo 群是練功場，不是檔案櫃。

**梯子底部：這不是生產力問題，是成長系統問題。** 北極星不是「省多少時間」，是「判斷有沒有更快變好」。

## 四、Eric 的五個回答＋兩個修正（原話為準）

1. **消費場合**：「寫文章、每天早上決定我要怎麼開啟一天、每週復盤」＋第 4 輪補：「新主題衍伸、看到文章或有靈感時想法在不同 repo 間碰撞」。
   → 敲定：任何功能必須出現在這些場合之一，否則不建。注意三個排程場合全在個人成長側，**週會報告未被提及**——本工具是個人系統，PM 工作訊號只是輸入，不是要產的報告。
2. **秘書還是教練**：「秘書 70%、教練 30%；彙整、追蹤、監控的資訊要先做好，才有教練的事情。」
   → 敲定建造順序；但配合第 4 答修正為：**秘書先開工，用教練的規格寫日誌**（呈現了什麼＋選了什麼，第一天就記）。
3. **與企業平台目標的關係**：「純自用，但工具我希望變成一個足以開源的專案。」
   → 敲定架構鐵律：私有資料與公開引擎第一天分離（repo 清單、路徑、偏好全走設定檔）。紅利：開發過程本身是發文輪值 W2（Agent Coding）的現成題材——工具餵寫作、寫作場合又是工具的客戶。
4. **回饋**：「對、回饋非常重要，只是彙整監控沒做好，還沒辦法管道回饋。」
   → 敲定依賴鏈：狀態彙整 → 回饋管道 → 教練。回饋是第五個痛點，暫被上游卡住，非不重要。
5. **品味怎麼知道變好**：「回顧以前的東西後，自己可以很清楚的知道我品味變好了。」
   → 敲定北極星的操作化：系統必須讓「當時的我」以可比較的形式被保存（當時的簡報、選擇、判斷依據），供日後重看。
6. **修正 A（第 4 輪）**：碰撞台是第四個場合——事件觸發、發散型，與三個排程儀式是不同物種；成敗變數是**啟動摩擦**（靈感半衰期以分鐘計）。
7. **修正 B（第 4 輪）**：「監控不是不做，還是要做，到體驗更好；體驗不好的監控形同虛設。」→ 監控升為**常駐環境層**，判準從「出現在哪個儀式」換成四條體驗測試（第八節）。

## 五、收斂後的一句話定義（v3）

> 我需要一個「**先當秘書、養出教練**」的個人循環系統。它在**三個排程儀式**（每天早上開工、寫文章、每週復盤）與**一個事件觸發的碰撞台**（靈感或文章到來的瞬間，把想法丟進一組 repo 對撞、必要時生出新 repo），把所有 repo 的訊號收斂成我能直接下判斷的形狀（秘書 70%）；**常駐環境層的監控**以「餘光可見、無事不報」的體驗存在；系統從第一天起用**教練的規格留痕**（看到什麼、選了什麼、依據是什麼），讓回饋管道在彙整成熟後接得上（教練 30%）。工具本體做成**足以開源的通用引擎**，我的資料留在私有層。北極星只有一個：**回顧過去的自己時，能清楚看見品味變好了。**

## 六、架構（v3 定形）

```

                     ║  餘光可見、無事不報 ║      資料採集用現成零件、體驗層自建
所有 repo 訊號 ──→   ╚═════════╦═════════╝
                               ↓
                ┌── registry（空間軸資產）──┐
                │  我有哪些牌、什麼狀態、    │  ← 全體功能的中心資料結構
                │  彼此什麼關係、tier、血統  │     （PM_Head registry.yaml 的個人超集）
                └────────────┬─────────────┘
                             ↓
                資料脊椎（時間軸資產，append-only 純文字）
                簡報快照｜我的選擇｜決策與依據｜建議與採納｜碰撞記錄
                             ↓
        ┌─ 儀式 1：早晨簡報（每天，排程）──「今天怎麼開場」＝系統心跳
        ├─ 儀式 2：寫作供料（每週 1-4 次）──選題與跨 repo 取材，接最成熟的寫作管線
        ├─ 儀式 3：週復盤（每週，排程）──教練 30% 住這裡；品味回顧按季在此放大
        └─ 碰撞台（事件觸發，秒級啟動）──發散型；四場合中唯一「需求已被自己手動驗證」的
```

第 1 輪三方向的歸位：方向 A（Context 食譜）＝碰撞台的「挑」＋儀式 2 的零件；方向 B（知識外溢對撞）＝碰撞台的「撞／落」＋「挑」的建議模式；方向 C 拆兩半＝「留痕格式」升格為脊椎（第一件事）、「夜間反芻引擎」仍最後做。**被淘汰的**：作為目的地的獨立儀表板（監控只以環境層形態存在）。（**2026-09-01 裁定修訂**：**監控台要做**——桌面工具內可開啟的監控視圖成立；被淘汰的重新定義為「**體驗不好的監控**」——預設面仍須過第八節四條判準（呈現異常與變化、自帶行動出口），全量狀態檢視降為可主動開啟的「深看模式」，不是預設面。）

## 七、操作單位：repo 組合，與「挑 → 撞 → 落 → 生」

素材檔 §1.2 懸而未解的問題（「我的操作單位不是檔案、不是程式碼，是什麼？」）在第 4 輪有了答案：

- **一手牌 ＝ repo 組合**：起手式從來不是「打開一個 repo」，是「這件事關係到哪幾個 repo」。
- **一張牌 ＝ 一個 repo，且牌要能快速生出來**：`020_Incubator/` 那排「等待 repo 化」的主題，是發牌太貴的直接證據。
- 整體即：**把 card_notes 的操作體驗放大到 repo 尺度**——卡片系統的 capture→對撞→拆卡→卡片網絡，在 repo 尺度對應 靈感→對撞→生 repo→repo 網絡。同一套代謝，兩個尺度。

碰撞台動詞鏈：

| 動詞 | 內容 | 速度要求 | 現成零件 |
|---|---|---|---|
| **挑** | 選出本次 repo 組合。三種模式成熟度遞增：手選（模糊搜尋 registry）→ 食譜（命名組合）→ 建議（系統依相關性主動提） | 秒級 | 部分有（mani 的 tag 分群、GitKraken Workspaces），但都不懂語意 |
| **撞** | 想法 vs 組合內容 → 已知／衝突／真增量 | 分鐘級 | 沒有；collide-capture 的推廣，獨門 |
| **落** | 結果路由：某 repo 的 `01_inbox/`、寫作素材、incubator | 自動 | 複用 inbox-dispatch 慣例 |
| **生** | 主題夠格時立新 repo | 分鐘級 | 骨架有（template/scaffold），「生完接進體系」沒有 |

**「生」採兩段式升格制**（防 repo 蔓生；平移 Eric 既有立場「Draft → Promotion Gate → Published」與「重複出現的 workflow 才升格成 skill」）：

1. 預設落點＝incubator 主題（一個 md，近零成本），每次碰撞都可生。
2. 主題**掙得** repo 身份才升格（被二次碰撞撞到、或真要開工）：模板展開、git init、**出生即登記進 registry**（含 tier 與血統：哪次碰撞生的它）。

卡片尺度的病史為證：便宜生產＋無衛生迴圈 → 86 張弱孤兒卡（占當時 32%）。repo 比卡片重得多，故**生得便宜，就要死得體面**——出生登記讓漂移從源頭消失（Text2SQL 未列管、department-agent-engineering 連漂移列表都沒進，皆「先生了、忘了登記」所致），退場走既有 tier 制度，由週復盤與環境層負責讓陳舊者浮上來。

## 八、監控的四條體驗判準（環境層的存在資格）

依據：BAT（15 欄 statusline、cache 過期警告、卡住偵測——監看做得細才有人用）、Orca（通知＋未讀語意）、審批疲勞研究（素材 3.8.1）。反面依據：workspace-stats / repo-healthcheck 建了沒人用——死因不是監控沒用，是**要人記得去看的監控沒用**。

| 判準 | 意思 | 病史反例 |
|---|---|---|
| **餘光可見** | 出現在我已經在的地方（statusline、簡報段落、推播），不是要「前往」的頁面 | 要主動跑指令的 healthcheck |
| **無事不報** | 正常時沉默，只浮出異常與變化，不丟全量狀態 | 掃出 86 張孤兒卡然後全部「待人工裁決」 |
| **有行動出口** | 每個警示自帶下一步（一鍵開碰撞、一鍵進 inbox） | 漂移列表從 7/21 掛到現在 |
| **打斷要自己掙得** | 只有不可逆、賠不起、系統自認沒把握才准打斷；其餘進未讀，等儀式時刻 | （預防性：審批疲勞研究結論） |

策略切分：**資料採集用現成零件，體驗層自建**——「什麼時候、以什麼形式出現在眼前」取決於四個場合，現成品不可能知道；且體驗層正是開源價值所在（BAT 證明此類工具的護城河是細節密度）。

> **2026-09-01 裁定補充（兩條）**：
> 1. **監控台確定要做**（可開啟的監控視圖）。四條判準約束的是它的**預設體驗**——預設面只呈現異常與變化並自帶行動出口；全量狀態屬「深看模式」（gitpane 的角色），要主動開啟。
> 2. **工具以通用引擎模式開發**：四個場合不是引擎功能，是 Eric 在私有層用引擎原語組裝的儀式（「通用引擎／私有資料分離」延伸為「通用引擎／私有儀式分離」）。判準相應改寫為「引擎原語能否組裝出四個場合」——組不出來＝功能有缺要補。

## 十、護欄（三條，對著病史設的）

1. **沒有場合，不建功能（修訂版）**：儀式類功能問「你出現在四個場合的哪一個」；監控類功能問「你過不過第八節四條體驗測試」。兩題都答不出→丟掉。（防「造工具 217 次 vs 用工具 23 次」復發）
   （**2026-09-01 補充裁定**：工具改以**通用引擎**模式開發後，場合不是引擎功能、是私有層的組裝，本護欄的問法相應變成「**這個原語被哪個場合的組裝用到**」——四個場合的組裝覆蓋測試在規格檔執行，覆蓋不到的原語同樣丟掉。）
2. **開源是畢業條件，不是起點**：架構第一天分離公私，但公開 repo 的整理工作要等「儀式連續跑滿四週」才准開始。（防開源打磨變成新的 logo 像素微調）
3. **教練規格從第一筆日誌開始**：秘書每次出手都留「呈現了什麼＋Eric 選了什麼」；教練行為可以晚到，資料一天不能缺。

## 十一、品味怎麼量（北極星的操作化）

品味進步不是儀表板數字，是**回顧時敢不敢、能不能面對過去的自己**。脊椎與 registry 使以下回顧成為可能：

- **靈感命中率**：三個月前的碰撞記錄，哪些後來長成了文章／repo／決策。
- **repo 存活率**：碰撞生出的主題，幾個升格了？升格的幾個還活著？（血統記錄使然）
- **決策回看**：當時的選擇與依據 vs 現在的結果（Obie `/decide` 式：連同當時考慮過的替代方案一起記）。

## 十三、開放問題（本檔不解，留給方案階段）

1. 三個儀式各自的**最小版本**長什麼樣（尤其早晨簡報第一版該含哪幾段）。
2. 碰撞台的**介面形態**：秒級啟動的載體是什麼（終端指令？hotkey？手機捕捉？）——四場合中最可能離開純終端的一個。
3. **registry 超集**的格式：擴充 PM_Head 的 `registry.yaml`，還是個人層另立一份、PM_Head 版成為其子集？
4. **脊椎 schema** 的具體欄位與檔案切分（每日一檔？每事件一列？）。
5. **公私切分線**的落點：哪些設定檔屬私有層、引擎以什麼形式讀取。
6. 與既有 skills 的**複用盤點**：repo-git-sync／commits-digest／inbox-dispatch／collide-capture 各自進入新架構的哪個位置。
7. 順序假說（待方案階段驗證）：脊椎格式最先；早晨簡報與碰撞台並列最早的兩件（一個養心跳、一個接住已驗證的需求）；監控體驗層從「簡報裡的一段」起步慢慢長成常駐；夜間反芻引擎最後。
